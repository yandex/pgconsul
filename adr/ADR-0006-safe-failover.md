# ADR-0006: Безопасный failover

**Статус:** Принято
**Дата:** 2026-09-30

# Context

## Определения

Обозначения primary `P`, durability members `D`, реплик `R(D, P)`, SSN, read и
write quorum, возможной write-конфигурации, cluster state, `state_id`, CAS,
leader lock и failover-manager lock определены в
[ADR-0005](ADR-0005-safe-durability-membership-change.md).

- **Failover** — аварийная смена primary после его отказа.
- **Switchover** — плановая смена primary, инициированная оператором.
- **Electorate** — зафиксированное при начале failover объединение `D` всех
  возможных write-конфигураций.
- **Probe** — ограниченная по времени попытка доказать недоступность текущего
  `desired_primary` до начала failover. Идентификатор probe равен `state_id`
  проверяемого cluster state.
- **Ответ probe** — свежая запись реплики с идентификатором probe,
  подтверждающая недоступность `desired_primary` из этой ревизии.
- **Durable LSN реплики** — позиция на фактическом timeline, перед которой все
  полные записи COMMIT сохранены в локальном WAL. Timeline и durable LSN
  определяются через `lwaldump_with_timeline()` после WAL-fence.
- **Результат голосования реплики** — атомарно записанные `state_id`, timeline,
  durable LSN и полная разобранная цепочка предков с fork LSN либо ошибка
  получения этих данных.
- **Результат голосования primary** — атомарно записанные `state_id`, timeline
  и полная разобранная цепочка предков без LSN. Перед публикацией узел в одной
  SQL-транзакции доказывает, что сейчас является primary этого timeline.
- **Валидный голос реплики** — результат от узла electorate, в котором
  `state_id` совпадает с текущим cluster state в фазе `failover/voting`;
  walreceiver остановлен до измерения, а timeline, durable LSN и полная history
  успешно получены.
- **Валидный голос primary** — результат от узла electorate, в котором
  `state_id` совпадает с текущим cluster state в фазе `failover/voting` и
  который опубликован после глобального WAL-fence. Узел должен оставаться
  primary проголосованного timeline, сохранить его WAL, а точная пара
  `(primary, timeline)` должна присутствовать в
  `possible_write_configurations`.
- **Timeline** — ветка истории WAL. Победитель выбирается только на одном из
  timeline, сохранённых в `possible_write_configurations`; остальные голоса
  используются для проверки скрытого WAL.
- **Switchpoint** — LSN, на котором потомок timeline ответвился от предка.
- **Проекция голоса на timeline** — durable LSN для голоса на самом timeline
  либо switchpoint первого перехода к timeline-потомку.
- **WAL-fence** — прекращение streaming WAL на реплике с подтверждением
  исчезновения walreceiver. Отключение archive restore выполняется best effort
  и в WAL-fence не входит.
- **Координатор** — держатель failover-manager lock, который меняет фазы
  failover и выбирает победителя.
- **Promotion** — выход PostgreSQL из recovery и переход в роль primary.

## Проблема и границы гарантии

Failover должен выбрать новый primary без потери транзакций, успешный коммит
которых был подтверждён клиенту. Хосты могут падать, перезапускаться и находиться
в разных сетевых партициях; координатор также может отказать на любом шаге.

Во время незавершённой смены durability members или предыдущего failover
транзакции могли подтверждаться несколькими write-конфигурациями. Поэтому новый
failover обязан проверить каждую запись `possible_write_configurations` и не
удалять их до успешного WAL-барьера нового primary.

Гарантия требует `fsync = on`, синхронного коммита с ожиданием flush, уникальных
`application_name` реплик и линеаризуемых CAS-операций ZooKeeper. Внешнее
изменение SSN, источников WAL или состояния failover не входит в гарантии ADR.
Принятые риски PostgreSQL перечислены ниже.

# Decision

## Состояние в ZooKeeper и фазы failover

Пути указаны относительно cluster prefix.

| Путь | Назначение |
|---|---|
| `/cluster_state` | Единая CAS-запись с `desired_primary`, `possible_write_configurations` и логической операцией. |
| `/failover_probe` | Идентификатор probe, равный проверяемому `state_id`. |
| `/failover_health/<fqdn>` | Ответ probe; свежесть определяется по mtime. |
| `/election_vote/<fqdn>` | Атомарный голос или ошибка, привязанные к `state_id` фазы `voting`. |
| `/failover_participant/<fqdn>` | Статус внешнего действия победителя, привязанный к разрешившему его `state_id`. |
| `/failover_manager`, `/leader` | Ephemeral-локи координатора failover и primary. |

Probe существует вне логической операции. После успешного начала failover
операция проходит следующие фазы:

| Фаза | Сохранённое состояние | Разрешённое действие |
|---|---|---|
| `voting` | `previous_primary`, electorate, `desired_primary = None` | WAL-fence, сбор голосов и выбор победителя. |
| `preparing` | Победитель и новый `target` сохранены, `desired_primary = None` | Победитель применяет SSN `target`. |
| `promoting` | `desired_primary` равен победителю | Получение leader lock, promotion и публикация фактического timeline. |
| `barrier` | Фактический timeline записан в последнюю конфигурацию | Новый primary выполняет WAL-барьер. |
| `idle` | Список схлопнут до фактической конфигурации | Failover завершён. |

Начало failover поверх незавершённой смены состава может выглядеть так:

```json
{
  "state_id": "f72e4c84-85ee-459f-b420-404f889d367a",
  "desired_primary": null,
  "operation": {
    "type": "failover",
    "phase": "voting",
    "failover": {
      "previous_primary": "P",
      "electorate": ["P", "A", "B", "C"]
    }
  },
  "durability": {
    "possible_write_configurations": [
      {"timeline": 12, "primary": "P", "members": ["P", "A", "B"]},
      {"timeline": 12, "primary": "P", "members": ["P", "A", "B", "C"]}
    ]
  }
}
```

Каждый переход фазы выполняется одним CAS и записывает новый `state_id`. Голоса
и статусы используются только в фазе и ревизии, которая разрешила действие.
Отдельной фазы cleanup нет.

## Владение и CAS

Координатор обязан удерживать failover-manager lock, но persistent owner в
cluster state не хранится. После истечения сессии отказавшего координатора новый
держатель читает сохранённую фазу и продолжает операцию. Живой зависший
держатель может задержать восстановление до истечения сессии; этот liveness-риск
принимается.

Получение manager lock само по себе не меняет cluster state. Перед каждым CAS
координатор заново читает состояние, проверяет `state_id`, фазу и результаты
внешних действий. Конфликт CAS требует повторного чтения; старые голоса и
статусы после смены `state_id` не используются.

Пока тип операции равен `failover`, обычный reconciliation durability members
не меняет cluster state или SSN.

Leader lock определяет узел, которому разрешено выполнять запись в PostgreSQL.
Новый победитель получает его только после WAL-fence всех возможных
write-конфигураций, записи себя в `desired_primary` и повторной проверки cluster
state.

## Probe и начало failover

Probe хранится отдельно от cluster state и не блокирует обычную смену durability
members. Реплика читает `desired_primary` и `possible_write_configurations` из
ревизии probe, проверяет недоступность именно этого primary и публикует ответ с
идентификатором probe.

Для каждой конфигурации `(D, P, T)` требуется `Q(D)` свежих ответов от
`R(D, P)`. Учитываются только ответы с текущим идентификатором, чья mtime входит
в срок жизни probe. Любой CAS cluster state меняет `state_id` и инвалидирует
probe со всеми ответами. Если список конфигураций не инициализирован или в нём
нет реплик, безопасный автоматический failover невозможен.

Первый хост, увидевший все probe quorum, получает failover-manager lock,
повторно читает probe, ответы и cluster state и одним CAS:

1. проверяет неизменность `state_id` и непустой `desired_primary`;
2. сохраняет текущий `desired_primary` как `previous_primary`;
3. фиксирует electorate как объединение `D` всех возможных конфигураций;
4. устанавливает `desired_primary = None`;
5. переводит операцию в `failover/voting`, не меняя
   `possible_write_configurations`;
6. записывает новый `state_id`.

Если предыдущая операция была switchover, сохраняется только необходимый для
восстановления контекст handoff. Если новый primary предыдущего failover успел
отказать до WAL-барьера, CAS новой попытки заменяет метаданные failover, но
сохраняет весь список возможных конфигураций.

Успешный CAS является единственной границей начала failover. До него primary
может продолжать reconciliation; конфликт CAS только инвалидирует probe и
запускает новую попытку для свежего состояния.

Автоматический failover запускается только когда запись через прежний primary
уже считается невозможной. Поэтому продолжающийся reconciliation не должен
бесконечно инвалидировать probe; если это всё же происходит, страдает liveness,
но не сохранность данных.

## WAL-fence и голоса

В failover используются три разных кворумных условия:

| Условие | Назначение |
|---|---|
| Probe quorum | `Q(D)` свежих ответов реплик доказывают основание начать failover. |
| Fence quorum | У `Q(D)` реплик остановлен walreceiver, поэтому primary конфигурации больше не имеет write quorum. |
| Election read quorum | Голос действующего primary его timeline либо `Q(D)` валидных голосов реплик дают данные для выбора. |

Ни одно из этих условий не заменяет остальные.

После начала failover previous primary по возможности закрывает пулер,
останавливает WAL-архивацию, освобождает leader lock и не пытается получить его
снова без нового разрешения. Пулер уменьшает число зависших клиентских
транзакций, а остановка архивации — объём лишнего WAL. Оба действия best effort:
невозможность нового подтверждённого коммита доказывает только fence quorum.

### Голос реплики

Перед голосованием реплика:

1. best effort отключает archive restore по процедуре ниже;
2. очищает `primary_conninfo`, запрашивает reload и ждёт исчезновения
   walreceiver;
3. получает timeline и durable LSN сканированием локального `pg_wal` через
   `lwaldump_with_timeline()`;
4. разбирает полную цепочку предков достижимого timeline с fork LSN;
5. атомарно записывает голос с `state_id` либо невалидный результат.

Receive LSN после рестарта PostgreSQL недоступен, replay LSN может отставать от
уже сохранённого WAL, а надёжного признака завершения replay локального WAL нет.
Поэтому другие наблюдаемые LSN не заменяют `lwaldump_with_timeline()`.

Ошибка сканирования или history не скрывается: такой результат не является
валидным голосом. До завершения выбора участник не выполняет rewind, не удаляет
WAL или history и не включает обратно источники WAL.

### Голос primary

Primary может голосовать только после fence quorum каждой возможной
конфигурации, в которой он указан как `P`. После этого его SSN всё ещё требует
write quorum, но подтвердить новый WAL уже некому.

Узел в одной SQL-транзакции на одном соединении проверяет
`pg_is_in_recovery() = false`, читает фактический timeline и разбирает его
history. Если PostgreSQL перезапустился или роль изменилась, голос не
публикуется. LSN не нужен: primary с сохранённым WAL содержит все транзакции,
которые были записаны на этом timeline, включая подтверждённые клиенту.

Координатор сопоставляет голос с `possible_write_configurations` текущего
`state_id`:

- если существует запись с этим узлом в `primary` и точно таким timeline, голос
  может использоваться как специальный голос primary;
- если узел вообще не указан как primary ни в одной записи, его прежняя
  write-конфигурация уже удалена. Выбор этого узла означает гарантированную
  потерю данных, поэтому узел исключается из кандидатов. Его голос не заменяет
  read quorum, но выбор продолжается среди остальных кандидатов;
- если узел указан как primary, но только с другим timeline, его фактическая
  история изменена вне протокола, например ручным promotion. Узел исключается
  из кандидатов с диагностикой ручного вмешательства, а выбор остальных
  кандидатов продолжается.

Такой голос сильнее голоса реплики. Он может сделать сам этот primary безопасным
кандидатом без read quorum его реплик, но не доказывает, что другой кандидат
содержит WAL primary.

### Глобальный WAL-fence и leader lock

До выбора победителя для каждой конфигурации `(D, P, T)` должно быть WAL-fenced
не менее `Q(D)` реплик из `R(D, P)`. Тогда у любого процесса, который считает
себя её primary, остаётся меньше `W(D)` реплик, способных подтвердить новый WAL.
Проверка выполняется для всех сохранённых primary и timeline, а не только для
последнего `desired_primary`.

После записи `desired_primary = None` координатор параллельно с WAL-fence даёт
previous primary время добровольно освободить leader lock. Принудительно
пересоздать ноду lock можно только после истечения таймаута и завершения
глобального WAL-fence. Каждый последующий acquire проверяет `desired_primary` и
`state_id` до и после операции ZooKeeper, поэтому старый primary не может
повторно получить lock.

### Best-effort отключение archive restore

Для попытки отключения pgconsul генерирует UUID и выставляет команду:

```conf
restore_command = 'echo <uuid> > <marker-path>.tmp && mv -f <marker-path>.tmp <marker-path>; false'
```

Один marker-файл используется только одним PostgreSQL-инстансом. Временный файл
находится рядом с ним, а атомарный rename заменяет marker предыдущей попытки без
промежутка между удалением и созданием. Завершающий `false` сообщает PostgreSQL,
что запрошенного файла нет. Совпадение UUID означает, что startup process вызвал
новую команду после завершения предыдущего restore.

Pgconsul ждёт marker не дольше `archive_restore_disable_timeout` из секции
`[replica]`; значение по умолчанию — 5 секунд. При таймауте голосование
продолжается: startup process мог не обработать SIGHUP или ещё проигрывать
локальный WAL. Ожидание не входит в WAL-fence и лишь уменьшает вероятность
наката за switchpoint и последующего rewind.

WAL или history, полученные до сканирования, учитываются в голосе. Полученные
после него не делают более ранний снимок небезопасным: архив сам по себе не
подтверждает синхронный коммит. Уже запущенный restore всё же может повлиять на
фактический timeline последующего promotion; этот риск описан ниже.

## Выбор победителя

Координатор начинает выбор только после глобального WAL-fence, проверки всех
голосов primary и получения election read quorum для каждой возможной
write-конфигурации. Для конфигурации read quorum образует валидный голос её
действующего primary на точном timeline либо `Q(D)` валидных голосов реплик из
`R(D, P)`. Timeline реплик не влияет на подсчёт кворума.

Координатор объединяет переданные цепочки history в дерево. Для одного номера
timeline во всех голосах должны совпадать parent и fork LSN. Противоречие или
невозможность однозначно расположить timeline сохранённой конфигурации блокирует
автоматический failover.

Для каждой конфигурации `(D, P, T)` голоса реплик проецируются на `T`:

- голос непосредственно на `T` проецируется в его durable LSN;
- голос потомка `T` — в fork LSN первого ребра от `T` к потомку;
- голос другой ветки не имеет проекции на `T`.

Для кандидата аналогично определяется граница содержащегося им WAL `T`: durable
LSN на самом `T`, fork LSN для потомка либо отсутствие WAL после общего предка
для другой ветки. Валидный голос primary непосредственно на `T` означает, что
сам этот primary содержит весь сохранённый WAL своего timeline.

Для кандидата, который не является проголосовавшим primary самой конфигурации,
координатор перебирает все реплики `R(D, P)`. Потенциальным носителем
подтверждённого commit, отсутствующего у кандидата, считается:

- непроголосовавшая реплика или реплика с невалидным результатом;
- валидно проголосовавшая на `T` или его потомке реплика, проекция которой не
  покрыта кандидатом.

Голос другой ветки не мог подтверждать WAL конфигурации `T` и не считается
носителем. Если потенциальных носителей не меньше `W(D)`, write quorum мог
подтвердить отсутствующий у кандидата commit, поэтому кандидат запрещён.
Кандидат допустим только после успешной проверки каждой записи
`possible_write_configurations`.

Проголосовавший primary точного timeline проходит проверку своей конфигурации
без LSN: никакая её реплика не может скрывать от него подтверждённую транзакцию.
Для остальных конфигураций он проверяется как обычный кандидат по истории WAL.

Все проголосовавшие кандидаты проверяются на всех timeline, сохранённых в
`possible_write_configurations`. Затем выбирается самый свежий допустимый
timeline от последнего выданного разрешения к старым. На одном timeline
выбирается максимальный durable LSN, затем hostname; точный голос сохранённого
primary имеет приоритет. Числовые LSN разных timeline не сравниваются, а голос
потомка нельзя объявить победителем на предке без rewind.

Например, при `W(D)=2` голос `A` с потомка timeline 2 проецируется на timeline 1
в switchpoint, `B` голосует на timeline 1 ниже switchpoint, а `C` не голосует.
Для кандидата `B` узлы `A` и `C` могут скрывать commit, поэтому `B` запрещён.
Кандидат на timeline 1, достигший switchpoint, покрывает голос `A`; тогда
потенциальным носителем остаётся только `C`.

Если допустимого кандидата нет, автоматический failover блокируется.

## Подготовка победителя

После выбора координатор одним CAS:

1. формирует `target` из всех валидно проголосовавших хостов, независимо от их
   текущего timeline;
2. для победителя-реплики рассчитывает новый разрешённый timeline, а для уже
   работающего primary использует его фактический timeline;
3. добавляет новую возможную write-конфигурацию с победителем и `target`;
4. сохраняет победителя, переводит операцию в `preparing` и меняет `state_id`.

Старые конфигурации остаются до WAL-барьера. Узлы с несовместимым WAL могут
войти в `target`, но начнут подтверждать WAL победителя только после rewind и
подключения к нему.

Победитель применяет `SSN(target, winner)` по ADR-0005 и публикует готовность с
текущим `state_id`. Для реплики это обязательно происходит до promotion. После
готовности и освобождения прежнего leader lock координатор CAS-записью
устанавливает `desired_primary = winner`, переводит операцию в `promoting` и
записывает новый `state_id`.

## Promotion и фактический timeline

Победитель может начать promotion или возобновить клиентскую запись, только
если он:

1. видит себя в `desired_primary`;
2. получил leader lock;
3. повторно проверил `state_id`, фазу `promoting` и `desired_primary`.

Остальные реплики только после записи нового `desired_primary` возвращают
обычный `restore_command`, записывают новый `primary_conninfo` и запрашивают
reload. Отдельное подтверждение применения обычного `restore_command` не
требуется. Дожидаться поворота кворума до promotion не нужно: участники
голосования остаются WAL-fenced и не могут принимать streaming WAL старого
primary.

Победитель-реплика выполняет promotion на новый разрешённый timeline. Уже
работающий primary promotion не выполняет, но проходит те же проверки перед
возобновлением записи. Неуспешный promotion не открывает клиентскую запись.

С патчем `target promote` PostgreSQL получает сохранённый timeline как явную
цель. Без патча pgconsul рассчитывает его как PostgreSQL 14:
`findNewestTimeLine(recoveryTargetTLI) + 1`. Кандидат не возобновляет archive
restore и walreceiver до promotion, но уже запущенный restore может добавить
history-файл и изменить фактический timeline.

После promotion победитель публикует фактический timeline с текущим `state_id`.
Координатор одним CAS при необходимости исправляет timeline последней возможной
конфигурации, переводит операцию в `barrier` и меняет `state_id`. Старые
конфигурации остаются. Обновление метаданных не задерживает клиентскую запись;
риск отказа до этого CAS описан ниже.

После записи нового `desired_primary` реплика освобождает прежний lease, пока её
локальный источник не совпадает с ним. После переключения источника она может
получить lease снова. Победитель освобождает replica lease после перехода в
primary. Прежний primary можно пометить для немедленного удаления из durability members, но смена `D`
всё равно выполняется по ADR-0005.

Если исход promotion неизвестен, другой победитель не выбирается, пока прежний
может удерживать leader lock. После потери lock запускается новый probe:
`previous_primary` берётся из текущего `desired_primary`, а новый failover
сохраняет все возможные конфигурации.

## WAL-барьер и завершение

В фазе `barrier` новый primary повторно применяет целевой SSN и выполняет
WAL-барьер с текущим `state_id`. Гарантии и ограничения SSN определены в
ADR-0005. Успешный статус публикуется с `state_id` этой фазы.

Координатор проверяет статус и одним CAS:

1. оставляет единственную последнюю конфигурацию с фактическими timeline,
   primary и members;
2. переводит операцию непосредственно в `idle`;
3. записывает новый `state_id`.

До этого CAS все старые конфигурации остаются значимыми. При отказе нового
primary следующий probe начинает новый failover и сохраняет весь список.
Локальные действия проигравших не образуют cleanup-фазу: они остаются
WAL-fenced до подключения к победителю.

Автоматический и ручной failover используют один алгоритм. Ручное разрешение
потери данных не входит в гарантии ADR.

## Восстановление после рестарта

| Фаза | Действие нового координатора или участника |
|---|---|
| `voting` | Продолжить WAL-fence и сбор голосов текущего `state_id`; при достаточных данных детерминированно повторить выбор. |
| `preparing` | Победитель повторно применяет SSN и публикует готовность; координатор после проверки переводит операцию в `promoting`. |
| `promoting` | Победитель повторно проверяет разрешение, получает leader lock, завершает или проверяет promotion и публикует фактический timeline. Неизвестный исход после потери lock начинает новый failover. |
| `barrier` | Новый primary повторяет применение SSN и барьер; координатор после успешного статуса выполняет завершающий CAS. |
| `idle` | Failover завершён. |

Все внешние действия и статусы идемпотентны в пределах разрешившего их
`state_id`. Статус другой ревизии не используется.

## Обоснование сохранности данных

Глобальный WAL-fence оставляет каждому сохранённому primary меньше `W(D)`
реплик, поэтому после снятия голосов ни одна возможная конфигурация не может
подтвердить новый commit.

Каждая ранее подтверждённая транзакция находится у primary своего timeline и на
write quorum его реплик. Точный голос primary используется только при наличии
соответствующей записи в `possible_write_configurations` и содержит весь такой
WAL. Если primary недоступен, election read quorum пересекается с write quorum,
и хотя бы один голос реплики содержит транзакцию.

Для каждого кандидата проверка потенциальных носителей отвечает на более
сильный вопрос: мог ли существовать целый write quorum с commit, отсутствующим у
кандидата. Проекция голоса потомка в switchpoint учитывает унаследованный WAL
предка, а непроголосовавшие и невалидные реплики считаются потенциальными
носителями. Кандидат разрешён только когда для каждой возможной конфигурации
таких носителей меньше `W(D)`.

Противоречивые history блокируют выбор. Если подтверждённые commit могли
находиться на несовместимых ветках, проверку всех конфигураций не пройдёт ни
один кандидат. Числовое сравнение LSN разных timeline для доказательства не
используется.

Новая конфигурация сохраняется вместе со всеми прежними. WAL-барьер переносит
весь WAL победителя на write quorum `target`; только после этого старые
конфигурации удаляются. Безопасность последовательных promotion следует
индуктивно: каждый новый выбор проверяет все конфигурации, которые ещё могли
подтверждать commit.

Доказательство условно относительно рисков применения SSN из ADR-0005 и двух
известных проблем ниже.

## Известные проблемы

### Sender старого timeline может подтвердить commit нового timeline

До promotion кандидат мог получить и отправить другой реплике WAL прежнего
timeline дальше будущего switchpoint. После promotion числовой LSN такого
подтверждения может быть больше LSN новой транзакции. Sync-rep PostgreSQL
сопоставляет ожидание commit с write/flush/apply LSN sender'а, не проверяя
timeline подтверждения.

Поэтому sender старого timeline может освободить ожидание commit нового
timeline, хотя WAL новой транзакции не попал на подтверждающую реплику.
Применение целевого SSN до promotion не закрывает гонку. Требуется изменение
PostgreSQL либо наблюдаемое подтверждение timeline каждого sender'а. Риск пока
принимается.

### Новый primary может подтвердить commit до сохранения фактического timeline

Без `target promote` фактический timeline может отличаться от записанного в
последней конфигурации. Клиентская запись после promotion не ждёт CAS, которым
координатор исправляет timeline.

Если primary подтвердил commit и отказал в этом окне, следующий failover увидит
устаревший timeline и не сможет корректно классифицировать фактическую ветку.
Риск пока принимается. Если primary остаётся доступен, публикация и CAS
повторяются до перехода в фазу `barrier`.

### Применение SSN

Гонки `SYNC_STANDBY_DEFINED` и смешанных конфигураций sender'ов описаны в
ADR-0005. Они могут нарушить предположение, что commit и WAL-барьер подтверждены
write quorum одной из сохранённых конфигураций. Этот риск также принимается.

# Alternatives

| Вариант | Почему отвергнут |
|---|---|
| Выбирать узел только по priority | Узел с большим priority может отставать от голоса read quorum и потерять подтверждённую транзакцию. |
| Собирать голоса из текущего списка alive-хостов | Исчезновение узлов после commit меняет electorate и позволяет выбрать реплику без записи. |
| Сравнивать LSN разных timeline | Числовой порядок LSN не задаёт порядок WAL на разных ветках. |
| Использовать receive или replay LSN вместо `lwaldump()` | После рестарта receive LSN потерян, а replay LSN может отставать от сохранённого `pg_wal`. |
| Записывать probe в cluster state | Одна изолированная реплика могла бы остановить смену durability members до кворумного доказательства отказа. |
| Не привязывать probe и голоса к `state_id` | Ответы могли бы относиться к уже изменившимся write-конфигурациям. |
| Хранить persistent owner failover | Persistent owner и ephemeral manager lock могут рассинхронизироваться после отказа координатора. |
| Требовать отдельный read quorum на выбранном timeline | Голоса потомков уже содержат WAL предка до switchpoint; отдельный кворум ветки излишне блокирует безопасный выбор. |
| Сначала доказывать, что новая ветка могла подтверждать транзакции | Это запрещает безопасного кандидата-потомка, который уже содержит весь WAL старой ветки. |

# Consequences

- Probe одной реплики не блокирует primary; failover начинается только после
  кворумного доказательства и CAS.
- Electorate и возможные write-конфигурации не зависят от изменяемого списка
  alive-хостов и переживают смену координатора.
- Ошибка `lwaldump()`, history или недостаток голосов не ослабляют гарантию, а
  могут заблокировать автоматический failover.
- Победить может безопасный кандидат на любом сохранённом timeline; конфликт
  history или возможные подтверждённые commit на несовместимых ветках блокируют
  выбор.
- Победитель применяет SSN и получает материализованное разрешение до promotion.
- Незавершённые failover увеличивают `possible_write_configurations`; успешный
  барьер снова сокращает список до одной записи.
- Размер списка ограничен максимальным размером znode ZooKeeper/ClickHouse
  Keeper. Если новая запись не помещается, автоматический failover останавливается:
  старую конфигурацию нельзя безопасно удалить без барьера.
- Принятые риски PostgreSQL перечислены явно и ограничивают доказательство
  сохранности данных.
