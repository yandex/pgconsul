# ADR-0005: Единый cluster state и разрешение на primary

**Статус:** Принято
**Дата:** 2026-11-13

---

# Context

## Определения

- **Текущий primary** — узел, на котором PostgreSQL фактически работает в роли
  primary.
- **`desired_primary`** — хост, которому сохранённое состояние кластера
  разрешает быть или стать primary. Это разрешение, а не утверждение о
  фактической роли PostgreSQL.
- **Возможная write-конфигурация `(D, P, T)`** — durability members `D`, их
  primary `P` и timeline `T`, для которых протокол выдал разрешение подтверждать
  транзакции; `P ∈ D`.
- **Набор реплик `R(D, P)`** — `D − {P}`.
- **Необходимое для кворумного коммита число реплик** —
  `W(D) = ceil(|R(D, P)| / 2) = floor(|D| / 2)`.
- **SSN** — `synchronous_standby_names`, задающий реплики, подтверждения которых
  ждёт primary. Обычное значение — `ANY W(D)(R(D, P))` либо пустая строка.
- **Write quorum** — любой набор из `W(D)` реплик, который мог подтвердить
  кворумный commit primary.
- **Read quorum** — любой набор из `Q(D)` реплик, где
  `Q(D) = |R(D, P)| − W(D) + 1`.
- **Логическая операция** — взаимоисключающий многошаговый процесс изменения
  конфигурации кластера. Операция проходит несколько фаз, CAS-записей,
  итераций и рестартов; одновременно активна не более чем одна операция.
- **Cluster state** — единая persistent-нода ZooKeeper `/cluster_state`,
  содержащая `desired_primary`, логическую операцию и все ещё значимые
  возможные write-конфигурации.
- **`state_id`** — UUIDv4 конкретной ревизии cluster state. Идентификаторы
  сравниваются только на равенство и не задают порядок.
- **CAS** — запись, которая выполняется только при совпадении прочитанной версии
  znode.
- **Failover-manager lock** — ephemeral-блокировка координатора failover.

## Проблема передачи primary

При switchover и failover есть необратимая граница: новому хосту уже разрешён
promotion, но результат ещё неизвестен. Он мог стать primary, мог продолжать
promotion после потери ZooKeeper-сессии или мог отказать до публикации
результата. В этом окне возвращать право старому primary без нового безопасного
выбора нельзя: оба хоста могли принимать запись на разных timeline.

Ephemeral leader lock не сохраняет это решение. Сессия может исчезнуть из-за
перегрузки или рестарта pgconsul, хотя запущенный promotion уже нельзя отменить.
Кроме того, исторически leader lock берётся из нескольких путей основного
цикла, switchover, failover и возврата в кластер. Проверка только rollback
switchover или временного `current_promoting_host` не защищает следующую
итерацию и рестарт процесса.

Поэтому разрешение на primary должно переживать потерю сессии и находиться в
состоянии, из которого восстанавливается весь протокол смены primary.

## Проблема раздельного состояния

Смену durability members, выбор primary и выполняемую операцию нельзя хранить в
независимых CAS-нодах. Например, старый primary может записать следующий шаг
перехода состава одновременно с началом failover, а switchover — отдельно
передать `desired_primary` и добавить write-конфигурацию нового primary. Обе
записи по отдельности успешны, но их сочетание не является состоянием ни одного
протокола.

Persistent owner операции рядом с ephemeral manager lock создаёт ту же
проблему: после отказа процесса lock освобождается, owner остаётся, и новый
координатор должен отдельным протоколом доказывать право его заменить.

# Decision

## Коротко, что предлагается

1. `desired_primary`, активная логическая операция и
   `possible_write_configurations` хранятся в одной persistent-ноде
   `/cluster_state` и меняются одним CAS.
2. `desired_primary` является единственным разрешением стать primary или
   открыть клиентскую запись, кроме уже открытой handoff-записи по ADR-0008.
   Leader lock не используется. Потеря ZooKeeper-сессии сама по себе не меняет
   разрешение.
3. Вне failover cluster state меняет только `desired_primary`; во время
   failover — держатель failover-manager lock. CAS-переход в failover разрешён
   отдельно.
4. `possible_write_configurations` содержит все ещё значимые выданные
   разрешения. Условия удаления записей определяет протокол конкретной операции.
   Граница передачи primary атомарно меняет `desired_primary`, фазу операции и
   список конфигураций.

## Структура cluster state

В устойчивом состоянии нода выглядит так:

```json
{
  "state_id": "d79a7d16-42f5-4b29-865b-1872c15da16d",
  "desired_primary": "P",
  "operation": {
    "type": "idle",
    "phase": null
  },
  "possible_write_configurations": [
    {"timeline": 12, "primary": "P", "members": ["A", "B", "P"]}
  ]
}
```

`operation.type` принимает значения `idle`, `durability_transition`,
`failover` либо `switchover`. Тип и фаза определяют обязательные метаданные,
разрешённого писателя и допустимый следующий переход. Данных cluster state
достаточно, чтобы после рестарта определить следующий идемпотентный шаг.

Массив `possible_write_configurations` упорядочен по выдаче разрешений. Его
последняя запись является самым новым разрешением, а в фазах с уже выбранной
целью — target текущей операции. Массивы, представляющие логические множества
FQDN, содержат каждый хост один раз и записываются в сортированном порядке.

Для cluster state действуют общие инварианты:

- список содержит все выданные write-конфигурации, которые протокол текущей
  операции ещё не разрешил удалить;
- в `idle` сохранена ровно одна конфигурация, её `primary` совпадает с
  `desired_primary`;
- если операция разрешает promotion или возобновление записи, последняя
  конфигурация описывает цель, а её `primary` совпадает с `desired_primary`;
- пустой список, неизвестная фаза или форма, не соответствующая операции,
  блокируют автоматическое изменение состояния.

Версия znode используется для CAS и не дублируется в JSON. `state_id` меняется
на новый UUIDv4 при каждом успешном CAS, даже если тип операции не изменился.

## Семантика `desired_primary`

Непустое значение даёт указанному хосту право:

- обслуживать клиентскую запись как primary;
- при необходимости выполнить promotion (только если фаза = promoting);
- менять cluster state вне failover, если текущая фаза разрешает конкретный
  переход.

Остальные хосты не открывают клиентскую запись и не выполняют promotion.
Единственное исключение для source во время handoff определено протоколом
switchover в ADR-0008. В остальных случаях хост, который фактически остался
primary после изменения `desired_primary`, закрывает пулер и следует протоколу
возврата в кластер.

Само значение не доказывает, что назначенный хост уже выполнил promotion:
фактическая роль и timeline проверяются отдельно.

`desired_primary = None` означает, что ни одному хосту не разрешено начинать
promotion или обслуживать клиентскую запись и не даёт узлу права самостоятельно
назначить себя.

Ошибка чтения, отсутствие обязательного поля или неизвестная фаза также не
дают права выполнить promotion, открыть пулер или изменить cluster state.
Ручной `pgconsul-util promote` не обходит это правило: хост должен уже быть
`desired_primary`, а текущая операция — разрешать promotion. Изменить
`desired_primary` можно только протоколом, который атомарно сохраняет связанные
write-конфигурации.

Замена недоступного `desired_primary` выполняется только протоколом failover из
ADR-0007.

Если cluster state отсутствует при первоначальной инициализации, локально
проверенный текущий primary может создать его операцией create-only, только
когда не выполняются failover или switchover. Существующий cluster state,
включая состояние с `desired_primary = None`, самоназначением не
перезаписывается. Некорректное или неполное состояние требует явного
восстановления.

## Владение и сериализация операций

Право записи определяется одновременно значением `desired_primary`, типом и
фазой операции:

| Операция | Кто меняет cluster state |
|---|---|
| `idle` | `desired_primary` |
| `durability_transition` | `desired_primary` |
| `switchover/tuning_ssn` | source, который остаётся `desired_primary` |
| `switchover/promoting` | target, записанный в `desired_primary` |
| `failover` | держатель failover-manager lock |

Перед внешним действием участник заново читает cluster state и проверяет
`state_id`, фазу и право на действие. После выполнения он проверяет фактический
результат и делает CAS по версии znode прочитанной ревизии без дополнительного
чтения. Конфликт CAS не считается успехом и требует перечитать состояние.
Операция не хранит persistent owner: право однозначно следует из текущего
состояния.

Failover-manager lock остаётся нужен для выбора одного координатора среди
нескольких хостов; его жизненный цикл определён в ADR-0007. Leader lock primary
не нужен: единственный разрешённый FQDN персистентно записан в cluster state, на
хосте работает один экземпляр сервиса, а `/alive/<fqdn>` отдельно показывает
живую ZooKeeper-сессию. Alive lock не даёт права быть primary и не заменяет
`desired_primary`.

## Атомарные границы протоколов

Связанные изменения `desired_primary`, операции и
`possible_write_configurations` выполняются одним CAS. Поэтому в cluster state
не появляется частично записанная граница операции. Конкретные переходы и
условия их выполнения определены в ADR-0006, ADR-0007 и ADR-0008.

# Alternatives

| Вариант | Почему не выбран |
|---|---|
| Использовать только ephemeral leader lock | Потеря сессии не отменяет уже разрешённый promotion и не доказывает, что право можно вернуть старому primary. |
| Хранить отдельную persistent-ноду `desired_primary` вместе с leader lock | Получаются два источника права на primary. Изменение разрешения нельзя атомарно связать с фазой операции и write-конфигурациями. |
| Использовать `current_promoting_host` | Временный флаг покрывает только часть promotion, может быть удалён до завершения восстановления и не описывает состояние после рестарта или новый безопасный выбор. |
| Исправить только rollback switchover | Leader lock исторически берётся из нескольких путей; следующая итерация или рестарт обходят локальное правило rollback. |
| Увеличить ZooKeeper session timeout | Это уменьшает вероятность ложной потери lock, но не устраняет отказ процесса и неопределённый результат promotion. |
| Хранить `desired_primary`, операцию и `possible_write_configurations` в разных CAS-нодах | Независимые писатели могут успешно сохранить несовместимые части разных логических состояний. |
| Хранить persistent owner операции | Он может пережить процесс и рассинхронизироваться с ephemeral manager lock; текущая фаза уже однозначно определяет писателя. |

# Consequences

- Необратимое разрешение на promotion переживает потерю ZooKeeper-сессии,
  итерацию и рестарт pgconsul; старый primary не получает право автоматически.
- Все протоколы используют одну форму состояния и один механизм recovery.
- CAS сериализует смену состава, failover, switchover и передачу
  `desired_primary`; при конфликте приходится перечитывать всю конфигурацию.
- Недоступный `desired_primary` может снизить доступность до безопасного начала
  failover. Это намеренная цена запрета самоназначения.
- Удаление leader lock требует, чтобы каждый путь promotion и открытия пулера
  проверял `desired_primary` и фазу операции. Прямые подключения к оставшемуся
  primary этим механизмом сами по себе не блокируются.
- Размер истории незавершённых write-конфигураций ограничен максимальным
  размером znode ZooKeeper/ClickHouse Keeper. Старую конфигурацию нельзя удалять
  только ради освобождения места.
