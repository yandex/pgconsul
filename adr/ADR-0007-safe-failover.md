# ADR-0007: Безопасный failover v1 для одного timeline

**Статус:** Принято
**Дата:** 2026-09-30

# Context

Обозначения primary `P`, durability members `D`, реплик `R(D, P)`, read quorum
`Q(D)`, возможной write-конфигурации, electorate, cluster state и `state_id`
приведены в [ADR-0005](ADR-0005-cluster-state-and-primary-authority.md).
Гарантии WAL-барьера приведены в
[ADR-0006](ADR-0006-safe-durability-membership-change.md).

Алгоритм применяется, когда все записи `possible_write_configurations`
относятся к одному timeline `T`. Failover должен выбрать новый primary без
потери подтверждённых клиенту транзакций и проверить каждую возможную
write-конфигурацию. Это первая версия безопасного failover, которая реализуется
первой. После реализации v2 обычный автоматический вход в failover заменяется
[ADR-0009](ADR-0009-failover-probe.md), правила голосования и выбора —
[ADR-0011](ADR-0011-safe-failover-two-timelines.md), а подготовка победителя,
promotion и завершение сохраняются. Ограничения и принятые риски описаны в
[ADR-0010](ADR-0010-failover-caveats.md).

- **Durable LSN** — позиция на фактическом timeline, перед которой все полные
  записи COMMIT сохранены в локальном WAL.
- **WAL-fence реплики** — остановка walreceiver с подтверждением его
  исчезновения.
- **Валидный голос** — подтверждение недоступности прежнего primary и
  опубликованные репликой `state_id`, timeline и durable LSN после WAL-fence.
  `state_id` должен совпадать с текущей фазой `failover/voting`, измерение
  должно завершиться успешно, а timeline должен быть равен `T`.

# Decision

## Состояние и фазы failover

Пути указаны относительно cluster prefix:

| Путь | Назначение |
|---|---|
| `/election_vote/<fqdn>` | Голос или ошибка, привязанные к `state_id` фазы `voting`. |
| `/failover_participant/<fqdn>` | Статус действия победителя, привязанный к разрешившему его `state_id`. |
| `/failover_manager` | Ephemeral-блокировка координатора failover. |

Failover начинается без отдельной probe. Реплика может попытаться запустить его,
если прежний `desired_primary` отсутствует среди alive-хостов, недоступен ей по
PostgreSQL-протоколу и истёк cooldown после предыдущей попытки. Первый хост,
получивший failover-manager lock, одним CAS:

1. сохраняет прежний `desired_primary` как `previous_primary`, но не меняет
   само значение `desired_primary`;
2. сохраняет исходную логическую операцию и все
   `possible_write_configurations`;
3. фиксирует electorate как объединение всех реплик `R(D, P)` сохранённых
   write-конфигураций;
4. переводит операцию в `failover/voting`, записывает новый `state_id`, дедлайн
   голосования и время, раньше которого нельзя начать следующую попытку.

Сохранённый `desired_primary` продолжает обслуживать клиентскую нагрузку и не
закрывает пулер из-за начала `voting`. Reconciliation durability members и
изменение SSN при этом замораживаются. Таким образом, ошибочное решение одной
реплики может до дедлайна остановить изменение состава, но не закрывает primary
от нагрузки. Переход незавершённого switchover в `voting` описан отдельно в
[ADR-0008](ADR-0008-safe-switchover.md).

Далее операция проходит `promoting` и завершается в `idle`.

В `promoting` последняя запись `possible_write_configurations` является
`target`, а её `primary` совпадает с `desired_primary`. Голоса и статусы
используются только с тем `state_id`, который разрешил действие. Отдельной фазы
cleanup нет.

## Голос реплики

В `failover/voting` участвуют все реплики всех write-конфигураций. Primary не голосуют.
Каждая реплика сначала независимо проверяет недоступность `previous_primary`.
Если primary доступен, реплика не выполняет WAL-fence и не голосует. Иначе перед
публикацией голоса она:

1. best effort отключает archive restore, сбрасывая `restore_command` по
   процедуре из [ADR-0010](ADR-0010-failover-caveats.md);
2. очищает `primary_conninfo`, запрашивает reload и ждёт исчезновения
   walreceiver;
3. получает timeline и durable LSN сканированием локального `pg_wal` через
   `lwaldump_with_timeline()`;
4. атомарно записывает голос с текущим `state_id` либо невалидный результат.

Timeline из `lwaldump_with_timeline()` просто сравнивается с `T` из
`possible_write_configurations`.

До завершения попытки реплика не выполняет rewind, не удаляет WAL и не включает
обратно источники WAL. Поэтому голос остаётся доказательством WAL-fence при
смене failover manager.

## Выбор победителя

Для каждой конфигурации `(D, P, T)` координатор должен получить `Q(D)` валидных
голосов от реплик `R(D, P)`. Их WAL-fence оставляет primary меньше `W(D)` реплик
и не позволяет подтвердить новый commit. Если кворума нет хотя бы для одной
конфигурации, автоматический failover не выбирает победителя. До получения этих
кворумов прежний primary может продолжать подтверждать транзакции. Каждый такой
commit пересекается хотя бы с одним будущим read quorum и содержится в голосе
реплики, которая выполнила WAL-fence после его подтверждения.

Если к дедлайну требуемые кворумы не собраны, координатор одним CAS возвращает
сохранённую до failover логическую операцию, оставляет прежние
`desired_primary` и `possible_write_configurations` и меняет `state_id`.
Реплики после этого возобновляют получение WAL. Следующая автоматическая
попытка разрешена только после cooldown; его срок сохраняется в cluster state и
переживает смену failover manager.

Побеждает реплика с максимальным durable LSN среди всех валидных голосов. На
одном timeline WAL образует общий префикс: read quorum каждой конфигурации
пересекается с её прежним write quorum, а максимальный LSN содержит данные всех
остальных валидных голосов.

## Владение и CAS

Координатор удерживает failover-manager lock; persistent owner в cluster state
не хранится. Новый держатель продолжает сохранённую фазу после истечения сессии
предыдущего координатора. Получение lock само по себе не меняет cluster state;
общие правила CAS определены в ADR-0005.

Пока операция имеет тип `failover`, обычный reconciliation durability members
не меняет cluster state или SSN. В `voting` прежний `desired_primary` сохраняет
право обслуживать клиентскую запись, но не меняет cluster state. Победитель
повторно проверяет разрешение перед promotion и открытием клиентской записи;
само значение `desired_primary` не доказывает, что promotion завершён.

## Подготовка победителя

Только после получения read quorum каждой возможной write-конфигурации
координатор одним CAS:

1. формирует `target` из всех валидно проголосовавших хостов;
2. рассчитывает новый разрешённый timeline для победителя;
3. добавляет новую возможную write-конфигурацию с победителем и `target`;
4. сохраняет победителя в `desired_primary`, переводит операцию в `promoting`
   и меняет `state_id`.

Старые конфигурации остаются до WAL-барьера. В `promoting` победитель применяет
`SSN(target, winner)` по ADR-0006 до promotion.

## Promotion и фактический timeline

Победитель может начать promotion, только если видит себя в `desired_primary`,
видит ожидаемые `state_id` и фазу `promoting` и непосредственно перед внешним
действием повторно прочитал ту же ревизию cluster state.

Остальные реплики после записи нового `desired_primary` возвращают обычный
`restore_command`, записывают новый `primary_conninfo` и запрашивают reload.
Дожидаться их поворота до promotion не нужно: участники голосования остаются
WAL-fenced и не могут принимать streaming WAL старого primary.

Победитель выполняет promotion на новый разрешённый timeline, повторно читает
cluster state и продолжает только при прежних `state_id`, фазе и
`desired_primary`. Затем он получает фактический timeline и при необходимости
CAS-записью исправляет timeline последней возможной конфигурации, оставляя
операцию в `promoting`. Старые конфигурации сохраняются. Расчёт разрешённого
timeline и риск расхождения с фактическим описаны в ADR-0010.

## WAL-барьер и завершение

Новый primary повторно применяет целевой SSN и выполняет WAL-барьер с текущим
`state_id`. Координатор принимает только успешный статус того же `state_id` и
одним CAS:

1. оставляет единственную последнюю конфигурацию с фактическими timeline,
   primary и members;
2. переводит операцию в `idle`;
3. записывает новый `state_id`.

До этого CAS прежние конфигурации остаются значимыми. Проигравшие остаются
WAL-fenced до подключения к победителю.

## Восстановление после рестарта

В `voting` новый координатор продолжает сбор голосов текущего `state_id` до
сохранённого дедлайна. После дедлайна он возвращает исходную операцию и
сохраняет cooldown. В `promoting` победитель повторно проверяет разрешение,
применяет SSN и при необходимости повторяет promotion, запись фактического
timeline и WAL-барьер. После успешного барьера координатор повторяет завершающий
CAS. `idle` означает завершённый failover.

# Alternatives

| Вариант | Почему отвергнут |
|---|---|
| Учитывать голос primary | Базовый алгоритм намеренно опирается только на WAL-fenced реплики. |
| Проецировать голоса между timeline | Для одного timeline проекции не нужны; расширение описано в ADR-0011. |
| Использовать receive или replay LSN | Эти позиции не доказывают наличие всего сохранённого локального WAL. |
| Выбирать узел только по priority | Узел с большим priority может отставать и потерять подтверждённую транзакцию. |
| Собирать голоса из текущего списка alive-хостов | Исчезновение узлов после commit меняет electorate и может скрыть запись. |
| Очищать `desired_primary` при входе в `voting` | Одна ошибочно запустившая failover реплика могла бы закрыть работающий primary от нагрузки до кворумного доказательства отказа. |
| Отдельная probe перед голосованием | Проверка недоступности входит в валидный WAL-fenced голос; отдельный набор ответов дублирует выборы. |
| Не привязывать голос к `state_id` | Голос мог бы относиться к уже изменившейся write-конфигурации. |
| Хранить persistent owner failover | Он может рассинхронизироваться с ephemeral manager lock после отказа координатора. |

# Consequences

- Алгоритм не требует разбора history.
- Electorate и возможные write-конфигурации не зависят от текущего списка
  alive-хостов и переживают смену координатора.
- Одна реплика может начать `voting` и временно заморозить reconciliation, но
  прежний primary остаётся открытым для нагрузки; повторные попытки ограничены
  cooldown.
- Несовпадение timeline, ошибка измерения или недостаток голосов блокируют
  автоматический выбор.
- Победитель применяет SSN и получает сохранённое разрешение до promotion.
- Старые write-конфигурации удаляются только после WAL-барьера победителя.
- Ограничения и принятые риски вынесены в ADR-0010.
