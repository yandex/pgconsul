# ADR-0004: Соглашение о `Factory` и `Config Builder` для инфраструктурных компонентов

**Статус:** Принято
**Дата:** 2026-08-05
**Автор решения:** kopylov74
**Тикет:** MDB-46662

---

## Контекст

`main.py` — God Object (около 2200 строк). Частично его разрастание вызвано
методами-конструкторами (`_commands()`, `_postgres_config()`), которые разбирают
`RawConfigParser` и знают детали секций INI (`global`, `commands` и т. д.). В ходе
декомпозиции по MDB-46662 нужна единая модель создания компонентов, чтобы `main.py`
оставался тонким оркестратором.

Единый шаблон уже сформировался в инфраструктурных компонентах. Текущее состояние:

| Компонент | Factory | Config Builder | Файл |
|-----------|---------|-----------------|------|
| `Zookeeper` | `create_zk(config)` | `(inline; технический долг)` | `zk.py` |
| `ReplicationManager` | `create_replication_manager(config, db, zk)` | `build_replication_manager_config(config)` | `replication_manager.py` |
| `SlotManager` | `create_replication_slot_manager(config, db, zk)` | `(inline; технический долг)` | `slot_manager.py` |
| `Postgres` | `create_postgres(config, cmd_manager)` | `build_postgres_config(config)` | `pg.py` |
| `CommandManager` | `create_command_manager(config)` | `build_command_manager_config(config)` | `command_manager.py` |

`Zookeeper` и `SlotManager` пока собирают конфигурацию внутри `Factory`. Это существующий
технический долг, а не прецедент для новых компонентов. Отдельный
`replication_manager_factory.py` был удалён в пользу размещения `Factory` рядом с классом.

Без документированного соглашения есть шансы нарушить этот шаблон.

---

## Решение

Каждый новый инфраструктурный компонент pgconsul создаётся парой функций,
расположенных в **том же модуле**, что и определение класса:

### 1. `build_<name>_config(config: RawConfigParser) -> <Name>Config`

- Разбирает одну или несколько секций INI и возвращает конфигурационный объект `@dataclass`.
- Новые проверки диапазонов выбрасывают `ValueError`; ошибки отсутствующих полей `configparser`
  распространяются. Существующее исключение: `quorum_removal_delay` ограничивается диапазоном 0–120 с предупреждением.
- Тестируется **без** создания самого компонента: тестам разбора конфигурации не требуются
  моки БД/ZK.

### 2. `create_<name>(config, *dependencies) -> <Name>`

- Вызывает `build_<name>_config(config)`, чтобы получить конфигурацию.
- Передаёт конфигурацию и уже созданные зависимости в конструктор класса.
- Зависимости внедряются как **готовые объекты**, но не как `RawConfigParser` и не через
  service locator.

### Правила

| Правило | Обоснование |
|------|-----------|
| `Factory` находится в **том же файле**, что и класс, а не в отдельном `*_factory.py` | Исключает лишний модуль, циклические импорты и обходные решения с отложенным импортом. |
| Конструктор и рабочие методы `Pgconsul` не разбирают INI | Собственную конфигурацию разбирает `build_pgconsul_config()` в `main.py`; конфигурацию зависимостей — их builders, кроме исключения ниже. |
| Конструктор класса принимает готовый `*Config` и зависимости, **не** `RawConfigParser` | Отделяет разбор от конструирования и позволяет писать unit-тесты без INI-файла. |
| `*Config` — это `@dataclass` (или `pydantic.BaseModel`), **не** `dict` | Типобезопасность, совместимость с `mypy --strict`, явные объявления полей. |
| `build_*_config` и `create_*` — **отдельные функции** | Разбор конфигурации можно тестировать изолированно; `Factory` остаётся тонкой обёрткой над `Config Builder`. |

### Исключение: компоненты с одним параметром

Когда компоненту требуется **ровно одно** скалярное конфигурационное значение,
пара `build_*_config` / `create_*` и `*Config`-dataclass создают несоразмерный
шаблонный код. В этом случае:

- Конструктор класса принимает скалярное значение напрямую, с типом (например,
  `log_timing_command: str | None`), **не** `RawConfigParser` и **не**
  однопольный `*Config`-dataclass.
- Фабричная функция не добавляется.
- `create_pgconsul()` читает единственное значение и передаёт его конструктору:
  `TimingTracker(zk, config.get('commands', 'log_timing', fallback=None))`.

Это единственное исключение из делегирования разбора конфигурации зависимостей их builders.

Прецедент: `TimingTracker` (`src/timings.py`).

### Направление внедрения зависимостей

Зависимости направлены внутрь согласно Dependency Rule (Clean Architecture):

```
main.py  →  create_<name>(config, db, zk, ...)
              │
              ├─ build_<name>_config(config) → <Name>Config
              │
              └─ <Name>(config, db, zk, ...)
```

Компонент не обращается наружу, чтобы создать собственные зависимости: вызывающий код
передаёт их ему (`Factory`, вызванная из `main.py`).

## Альтернативы

| Вариант | Причина отклонения |
|---------|--------------------|
| Отдельный `*_factory.py` | Лишний модуль, циклические импорты и расхождение с существующим шаблоном. |
| Конструктор разбирает `RawConfigParser` | Смешивает ответственность и ухудшает изолированное тестирование. |
| Service locator / DI-контейнер | Избыточен, скрывает граф зависимостей и вводит новые отказы. |
| Не документировать соглашение | Решение не очевидно, а новые компоненты могут нарушить шаблон. |

## Последствия

### Положительные

- Разбор INI отделён от рабочей логики компонентов и оркестратора.
- Разбор конфигурации тестируется изолированно: `TestBuildPostgresConfig` и
  `TestBuildCommandManagerConfig` запускаются без моков БД/ZK.
- Новые компоненты следуют единому шаблону, поэтому участникам нужно реже решать,
  «как это создать».
- Граф зависимостей явен в `create_pgconsul()`, сохраняя ясность порядка запуска.

### Отрицательные

- Кроме исключения с одним параметром, компоненту нужны две функции и конфигурация `@dataclass`: это больше
  шаблонного кода, чем один конструктор.
- Зависимости нужно создать **до** вызова `Factory`, поэтому порядок вызовов `create_*`
  в `create_pgconsul()` важен. Например, `create_postgres` требует `cmd_manager`, значит
  `create_command_manager` должен быть вызван раньше. Это намеренно и видно в коде, но требует поддержки.
- Компонент с динамически разрешаемой зависимостью (например, «создать `db` только после
  подключения ZK») плохо соответствует статической модели `Factory`: таким случаям нужна
  ленивая `Factory` или двухфазная инициализация, которые этот ADR не описывает.

---

## Область действия

**В области действия:** создание новых инфраструктурных компонентов. Inline-разбор конфигурации в существующих
`Zookeeper` и `SlotManager` считается техническим долгом; этот ADR не требует его немедленного устранения.

**Не входит в область действия:**
- Соглашения об именовании классов (`CamelCase` и т. п.): это стиль, а не архитектура.
- Контракты обработки ошибок: их покрывают ADR-0001 и ADR-0002.
- Порядок операций итерации.
