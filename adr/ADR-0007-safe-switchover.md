# ADR-0007: Безопасный switchover

**Статус:** Принято
**Дата:** 2026-11-13

# Context

Обозначения primary `P`, durability members `D`, реплик `R(D, P)`, SSN,
возможной write-конфигурации, cluster state, `state_id`, CAS,
`desired_primary` и WAL-барьера определены в
[ADR-0005](ADR-0005-safe-durability-membership-change.md).

- **Switchover** — плановая смена primary, запрошенная оператором.
- **Source primary** — текущий primary `P`, который начинает switchover.
- **Target primary** — выбранная реплика `C`, которая должна стать новым
  primary.
- **`D0`** — durability members единственной write-конфигурации перед началом
  switchover; `T0` — её timeline.
- **Handoff SSN** — временный SSN source primary, при котором каждый новый
  подтверждённый commit обязательно записан на `C`.
- **Switchover request** — отдельная persistent-нода ZooKeeper со статусом,
  уникальным `request_id`, таймаутом и необязательными ограничениями
  `source_primary` и `target_primary`.

Во время switchover source primary может продолжать запись, пока target и
остальные реплики готовятся к смене источника. При этом ZooKeeper, SSN,
фактические роли PostgreSQL и подключения реплик нельзя изменить атомарно.
Протокол должен исключать как потерю подтверждённого commit, так и откат к
source primary после того, как target уже получил разрешение на promotion.

# Decision

## Коротко, что предлагается

1. CLI создаёт отдельный запрос со статусом `requested`, таймаутом и
   необязательными source и target. Текущий primary ждёт, пока в
   `possible_write_configurations` останется одна запись, выбирает target и
   начинает `switchover/tuning_ssn`, не меняя `desired_primary`.
2. Source primary делает target обязательной синхронной репликой. С патчем он
   сохраняет прежний кворум; без патча временно сжимает состав до source и
   target. После применения SSN source выполняет WAL-барьер.
3. Source одним CAS устанавливает `desired_primary = target`, добавляет
   write-конфигурацию нового primary и переходит в `switchover/promoting`.
4. Target до promotion применяет SSN новой конфигурации. Реплики поворачиваются
   на target; source прекращает работу, когда больше не может подтвердить
   commit либо когда у него остаётся только target. Target выполняет promotion
   после подключения своего write quorum либо когда не повернулся только
   source.
5. Новый primary записывает фактический timeline, выполняет WAL-барьер,
   переводит запрос в `done` и одним CAS оставляет новую конфигурацию
   единственной. Если deadline истёк до handoff, source переводит запрос в
   `failed` и отменяет switchover. Если deadline истёк после handoff, любой
   хост может взять failover lock и запустить обычный `failover/voting`.

## Запрос и начало switchover

CLI создаёт `/switchover_request` и не меняет cluster state. Запрос содержит:

- `request_id` — UUID запроса;
- `status` — `requested`, `in_progress`, `done` либо `failed`;
- `timeout` — предельная длительность switchover; если поле не задано,
  используется значение из конфигурации pgconsul;
- `source_primary` — необязательный хост, с которого разрешён switchover;
- `target_primary` — необязательный хост, на который разрешён switchover.

Новый запрос не перезаписывает `requested` или `in_progress`. Запрос в `done`
или `failed` можно заменить новым через CAS. Если указан `source_primary`,
принять запрос может только этот хост. Если указан `target_primary`, выбрать
можно только его.

Текущий `desired_primary` начинает switchover только из `idle` с одной записью
`(D0, P, T0)` в `possible_write_configurations`. Пока смена durability members
не закончена, запрос остаётся ждать. Target должен быть доступной репликой из
`D0 − {P}`, которая получает WAL от source. При явно заданном target выбирается
только он; иначе используется обычный порядок приоритетов. Выбор сохраняется в
операции и после этого не меняется.

Одним CAS source primary:

1. переводит операцию в `switchover/tuning_ssn`;
2. сохраняет `request_id`, source, target, исходный состав `D0` и абсолютный
   `deadline`, рассчитанный из таймаута запроса;
3. оставляет `desired_primary = P`;
4. записывает новый `state_id`.

После успешного CAS source переводит запрос с тем же `request_id` в
`in_progress`. При отказе между этими записями cluster state уже содержит всю
операцию, поэтому source повторяет смену статуса и не запускает второй
switchover.

## Фазы и владение

| Фаза | `desired_primary` | Кто меняет cluster state | Назначение |
|---|---|---|---|
| `tuning_ssn` | source | source | До deadline настроить source так, чтобы target подтверждал каждый commit, затем выполнить WAL-барьер. |
| `promoting` | target | target | Применить SSN нового primary, переключить на него реплики, выполнить promotion после подключения write quorum либо когда не повернулся только source, затем выполнить барьер. |
| `idle` | target | target | Switchover завершён; конфигурация нового primary осталась единственной. |

Каждый CAS записывает новый `state_id`. До смены `desired_primary` только source
продвигает операцию. После неё cluster state меняет только target; source лишь
проверяет возможность commit и меняет собственную роль.

В `switchover/promoting` source может временно оставаться фактическим primary,
хотя `desired_primary` уже указывает на target. Это узкое исключение из обычной
семантики `desired_primary`: source разрешено только закончить обслуживание
записи через заранее установленный handoff SSN. Он не меняет cluster state, не
может повторно выполнить promotion и после остановки не возвращается в роль
primary.

## Подготовка handoff

В `tuning_ssn` source должен передать target весь уже записанный WAL и сделать
его обязательным участником каждого следующего commit.

С патчем синхронно-кворумной репликации source сохраняет исходный кворум и
применяет:

```text
EVERY(C), ANY W(D0)(R(D0, P))
```

Это условие строже обычного SSN конфигурации `(D0, P, T0)`: оно не разрешает ни
одного дополнительного варианта commit. Поэтому
`possible_write_configurations` не меняется и по-прежнему содержит только
`(D0, P, T0)`.

Без патча source выполняет внутри switchover обычный переход по ADR-0005 к
конфигурации с `members = {P, C}` и `SSN = ANY 1(C)`. `(D0, P, T0)` и
`({P, C}, P, T0)` сохраняются до WAL-барьера; после него остаётся только
`({P, C}, P, T0)`. Если исходный состав уже равен `{P, C}`, новая запись не
добавляется: source применяет тот же SSN и выполняет барьер.

В обоих вариантах после применения handoff SSN source выполняет WAL-барьер.
Барьер доказывает, что target получил весь предшествующий WAL, а handoff SSN
гарантирует получение target всех последующих подтверждённых commit до
разрыва его соединения с source.

До успешного барьера `desired_primary` остаётся равен `P`. Ошибка до deadline
оставляет операцию в `tuning_ssn` для следующей попытки. После deadline source
больше не переходит к handoff и начинает отмену switchover, описанную ниже.

## Передача primary

После подготовки source одним CAS:

1. добавляет в конец `possible_write_configurations` конфигурацию
   `(D0, C, Tnew)`, где `Tnew` — timeline, который должен создать promotion;
2. устанавливает `desired_primary = C`;
3. переводит операцию в `switchover/promoting`;
4. записывает новый `state_id`.

Последняя конфигурация является целью операции: её `primary = C` совпадает с
`desired_primary`. Поэтому `C` в начале любой итерации получает из cluster
state будущий SSN, ожидаемый timeline и число реплик, которое должно
подключиться до promotion.

Этот CAS является необратимой границей handoff. После него switchover не
возвращает `desired_primary` на source: target уже мог выполнить promotion и
подтвердить commit на новом timeline.

## Параллельные действия в `promoting`

После handoff действия хостов идут параллельно:

- `C`, ещё оставаясь репликой, применяет
  `SSN = ANY W(D0)(R(D0, C))` и продолжает получать WAL от `P`. Он выполняет
  promotion на `Tnew`, когда к нему подключились `W(D0)` реплик либо когда к
  нему повернулись все узлы из `D0 − {P, C}`, то есть не повернулся только `P`;
- реплики из `D0 − {P, C}` меняют источник с `P` на `C`;
- `P` постоянно проверяет по `pg_stat_replication`, может ли его handoff SSN
  подтвердить commit и какие реплики из `D0` ещё к нему подключены. Когда
  commit становится невозможен либо из этих реплик остаётся только `C`, `P`
  закрывает пулер, прекращает работу как primary и возвращается в кластер как
  реплика `C`.

При promotion `C` выходит из recovery и перестаёт получать WAL от `P`.
Handoff SSN обязательно требует подтверждения `C`, поэтому с этого момента
старый primary уже не может подтвердить новый commit. С патчем это может
произойти ещё раньше, если от `P` отключилось слишком много других реплик.

Все commits, которые `P` успел подтвердить до promotion `C`, уже сохранены на
`C`. Commit, которому после promotion не хватило подтверждения, клиенту не
подтверждён. До promotion нельзя рассчитывать на `P` как на одну из реплик
`C`: после остановки у него может остаться WAL дальше позиции `C`, и для
возврата может потребоваться rewind уже с нового timeline.

Если `C` промоутился по условию «не повернулся только `P`», доступного write
quorum у него может ещё не быть. В этом случае его SSN не позволит подтвердить
клиентский commit, пока `P` не вернётся как реплика. Для двуххостового кластера
это является обычным путём switchover.

Подключение реплик к `C` до promotion допустимо: PostgreSQL позволяет standby
передавать полученный WAL каскадным репликам. Само соединение не доказывает,
что реплика уже догнала `C`; после promotion синхронный commit при
необходимости дождётся её flush.

## Timeline, WAL-барьер и завершение

После promotion `C` повторно читает cluster state и продолжает только при
`operation = switchover/promoting` и `desired_primary = C`. Если PostgreSQL
создал не `Tnew`, `C` CAS-записью исправляет timeline последней конфигурации и
заново читает состояние.

Затем `C` выполняет WAL-барьер с текущим `state_id` и переводит запрос с тем же
`request_id` из `in_progress` в `done`. После этого `C` одним CAS:

1. оставляет последнюю фактическую write-конфигурацию единственной;
2. переводит операцию в `idle`;
3. записывает новый `state_id`.

Смена статуса запроса и финальный CAS намеренно не атомарны. `done` означает,
что promotion и завершающий WAL-барьер уже успешны; cluster state может ещё
оставаться в `switchover/promoting`. Если `C` откажет в этом окне, после
рестарта он повторит финальный CAS. Новый запрос, заменивший терминальный через
CAS, будет ждать перехода cluster state в `idle`.

## Отказы и возобновление

- Если deadline истёк в `tuning_ssn`, `P` переводит совпадающий запрос в
  `failed`, а затем CAS-записью переводит cluster state в `idle`, сохраняя
  `desired_primary = P` и текущие `possible_write_configurations`. К handoff он
  больше не переходит; незавершённую смену durability members продолжает
  обычный алгоритм.
- В `tuning_ssn` статус `failed` означает, что разрешение на handoff не выдано;
  безопасное сворачивание операции при этом может ещё продолжаться. Отказ между
  записью `failed` и CAS в `idle` оставляет достаточно состояния для повторения
  cleanup. После handoff `failed` означает, что завершение передано failover.
- После возврата в `idle` обычный алгоритм смены durability members приводит
  сохранённую конфигурацию к желаемому `D0`. С PostgreSQL-патчем состав уже
  равен `D0`; алгоритм должен лишь убрать из SSN switchover-ограничение
  `EVERY(C)`. Барьер для этого не нужен: удаление `EVERY(C)` возвращает SSN,
  уже описанный единственной сохранённой конфигурацией `(D0, P, T0)`.
- Если deadline истёк в `promoting`, безусловный откат к `P` запрещён. Любой хост может
  взять failover lock, повторно прочитать cluster state и CAS-записью перевести
  всё ещё актуальную операцию `switchover/promoting` в обычный
  `failover/voting`. Для такого failover не задаётся исходный хост: он сохраняет
  все `possible_write_configurations`, заново проверяет фактическое состояние
  кластера и выбирает безопасный primary по алгоритму ADR-0006. После успешного
  перехода запрос switchover переводится в `failed`.
- В `promoting` `C` повторяет применение своего SSN, ожидание реплик,
  promotion, публикацию фактического timeline и WAL-барьер. `P` и остальные
  реплики повторяют только смену локальной роли или источника.
- До handoff работают обычные правила запуска failover из ADR-0006. После
  handoff они больше не проверяются: единственным основанием начать failover
  становится истечение deadline switchover, описанное выше.
- Неизвестный результат внешнего действия не считается успехом. Следующая
  итерация проверяет фактическое состояние и продолжает ту же фазу.

## Обоснование сохранности данных

До handoff каждый новый подтверждённый commit находится на `C`: это
обеспечивает `EVERY(C)` либо `ANY 1(C)`. Подготовительный WAL-барьер передаёт
на `C` и весь WAL, записанный до применения handoff SSN.

После handoff конфигурация `P` сохраняется в
`possible_write_configurations`. Во время promotion `C` перестаёт получать WAL
от `P`, и `P` теряет обязательное для commit подтверждение. До promotion `C`
применяет свой SSN. Если его write quorum ещё не подключён, этот SSN блокирует
новые commit до возвращения недостающих реплик. Поэтому `P` и `C` не могут
одновременно подтверждать независимые commit.

Завершающий WAL-барьер переносит весь WAL нового primary на его конфигурацию.
Только после этого старую конфигурацию можно удалить.

Гарантия применения SSN имеет те же ограничения PostgreSQL, которые описаны в
ADR-0005. Этот ADR не добавляет отдельного механизма подтверждения его
распространения по процессам PostgreSQL.

# Alternatives

| Вариант | Почему не выбран |
|---|---|
| Сразу остановить source, затем выполнить promotion | Даёт более длинный период недоступности записи и не использует возможность безопасно готовить реплики параллельно. |
| Разрешить откат на source после записи `desired_primary = target` | Target уже мог создать новый timeline и подтвердить commit; без failover-голосования безопасность отката недоказуема. |
| Хранить ход switchover только в отдельных нодах | Отдельные записи могут разойтись с `desired_primary` и durability state. Запрос остаётся отдельным, а выполняемая операция хранится в едином cluster state. |

# Consequences

- С патчем синхронно-кворумной репликации исходный кворум сохраняется до
  handoff. Без патча write-конфигурация временно сжимается до source и target,
  что снижает доступность при отказе одного из них.
- Обычно promotion ждёт write quorum будущего primary. Если не повернулся
  только source, promotion разрешён раньше, но клиентские commit блокируются
  SSN до его возвращения. Это позволяет выполнить switchover в двуххостовом
  кластере без ослабления целевой write-конфигурации.
- После необратимой границы любая неопределённость разрешается через failover,
  а не возвратом к source.
