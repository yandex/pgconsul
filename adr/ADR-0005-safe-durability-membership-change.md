# ADR-0005: Безопасная смена состава durability members

**Статус:** Принято
**Дата:** 2026-09-16

---

## Контекст

Durability members — это сохранённый в ZooKeeper набор узлов, чьи WAL могут
участвовать в принятии решения о failover. В него входит текущий primary `P`.
PostgreSQL независимо хранит конфигурацию синхронной репликации в
`synchronous_standby_names` (SSN). Эти два хранилища нельзя изменить атомарно.

Для состава `D`, содержащего `P`, обозначим набор реплик как `R(D, P) = D − {P}`.
При кворумной синхронной репликации PostgreSQL использует:

```text
W(D) = ceil(|R(D, P)| / 2) = floor(|D| / 2)
ANY W(D)(R(D, P))
```

Для failover нужен read quorum:

```text
Q(D) = |R(D, P)| − W(D) + 1
```

Любой набор реплик, подтвердивших запись, размером `W(D)`, пересекается с
любым набором голосов размером `Q(D)`. Поэтому победитель, подтверждённый
`Q(D)` валидными голосами, не может не содержать WAL подтверждённой клиенту
записи.

Простой порядок «сначала ZooKeeper, затем SSN» небезопасен. Например, при
переходе `[P,A,B]` с `ANY 1(A,B)` к `[P,A,B,C]` с `ANY 2(A,B,C)` ZooKeeper
может уже разрешить новую конфигурацию, пока SSN ещё старый. Если запись есть
только на `A`, а `P` и `A` недоступны, голоса `B,C` могут выбрать узел без этой
записи.

Обратный порядок также небезопасен для некоторых сжатий. Значит, нельзя
выбирать порядок только по тому, расширяется или сжимается набор.

## Решение

Каждая смена состава выполняется одним протоколом. В ZooKeeper хранится либо
стабильный состав, либо переход с `source`, `target` и новым `operation_id`.
Стабильным считается `source` до завершения всех шагов.

1. Primary CAS-записью создаёт intent: `source`, `target`, `operation_id`.
2. Primary применяет SSN, вычисленный для `target`, и ждёт, пока PostgreSQL
   подтвердит, что конфигурация действует.
3. По неблокирующему соединению primary записывает WAL-барьер и коммитит его с
   `synchronous_commit = on`:

   ```sql
   BEGIN;
   SET LOCAL synchronous_commit = on;
   CREATE TABLE IF NOT EXISTS public.pgconsul_durability_barrier (
       singleton boolean PRIMARY KEY CHECK (singleton),
       operation_id text NOT NULL
   );
   TRUNCATE TABLE public.pgconsul_durability_barrier;
   INSERT INTO public.pgconsul_durability_barrier
       (singleton, operation_id) VALUES (true, '<operation_id>');
   COMMIT;
   ```

4. Только после успешного барьера primary CAS-записью делает `target`
   стабильным составом и удаляет переход.

Успешный синхронный коммит означает, что весь WAL primary до барьера был
сброшен набором подтверждающих реплик из `target`. Этот набор пересекается с
любым read quorum `target`; последующие транзакции уже защищены SSN `target`.

Барьер выполняется неблокирующе: незавершённая команда не блокирует основную
итерацию pgconsul. Таймаут или потеря соединения не считаются успехом, поскольку
локальный коммит мог завершиться до получения подтверждения клиентом.

### Восстановление после рестарта

| Точка остановки | Сохранённое состояние | Действие после рестарта |
|---|---|---|
| До intent | Старый стабильный состав | Начать переход заново. |
| После intent, до SSN | `source`, `target`, `operation_id` | Применить SSN `target`. |
| После SSN, до барьера | Переход сохранён | Повторно применить SSN и барьер. |
| После барьера, до финального CAS | Переход сохранён | Повторить барьер и CAS для `target`. |
| После финального CAS | Стабильный `target`, перехода нет | Считать операцию завершённой. |

Повторное применение SSN, барьера и CAS безопасно, пока primary не сменился.
Конфликт CAS требует заново прочитать состояние; он не является признаком
успешного завершения.

### Failover во время перехода

До отказа primary подтверждённые записи могли быть сделаны как со старым, так
и с новым SSN. Поэтому при переходе `source → target` failover проверяет оба
состава.

Для каждого `D` из `(source, target)` необходимо:

1. получить `Q(D)` валидных, fenced-голосов от `R(D, P)`;
2. выбрать кандидата, чей durable LSN не отстаёт от LSN как минимум `Q(D)`
   этих голосов.

Один и тот же кандидат обязан пройти обе проверки. Получить два кворума
недостаточно: самые новые данные могут находиться у разных реплик. Победителя
выбирают из electorate стабильного (`source`) состава. После promotion
незавершённый переход CAS-очисткой удаляется вместе с данными failover, а
обычная сверка позднее создаёт новый переход, если `target` по-прежнему нужен.

Если первоначальный стабильный состав ещё не записан, failover запрещён: нет
предыдущего SSN, относительно которого можно доказать безопасность.

### Допустимые формы перехода

Обычная сверка выполняет расширение по одному хосту. Чистое сжатие может
удалить несколько хостов за один переход. Замена реплик представляется как
несколько однохостовых расширений, затем одно чистое сжатие.

Произвольная прямая замена может сделать failover излишне недоступным, пока
переход не завершён: для `source=[P,A,B]`, `target=[P,A,C]` потребуются голоса
и от `B`, и от `C`, хотя один `source` мог бы выбрать кандидата. Чистое сжатие
этой проблемы не создаёт, так как не вводит новую реплику.

В частности, surviving primary может сразу сжать `[P,A,B,C]` до `[P]`, если
все реплики потеряны. SSN становится асинхронным, барьер коммитится локально,
и доступность записи восстанавливается. До добавления новой реплики такой
кластер намеренно не даёт автоматическому failover гарантий сохранности.

### Владение и блокировки

Один ограниченный шаг reconciliation — единственный код, который начинает или
продвигает переход. Он выполняется в ZooKeeper-backed итерации после обновления
maintenance state. Менять состав и SSN может только узел, владеющий leader
lock.

Обычная смена состава удерживает primary lock и election-manager lock, после
чего повторно проверяет отсутствие активного failover. Failover, switchover и
return-to-cluster не изменяют стабильный состав напрямую.

## Альтернативы

| Вариант | Проблемная ситуация |
|---|---|
| Всегда «ZooKeeper, затем SSN» | `[P,A,B]`, `ANY 1(A,B)` меняется на `[P,A,B,C]`, `ANY 2(A,B,C)`. Пока SSN старый, запись может быть только на `A`; после потери `P,A` голоса `B,C` выберут узел без неё. |
| Всегда «SSN, затем ZooKeeper» | `[P,A,B,C]`, `ANY 2(A,B,C)` сжимается до `[P,A,B]`, `ANY 1(A,B)`. Пока ZooKeeper старый, запись может быть только на `A`; после потери `P,A` старый quorum `B,C` выберет узел без неё. |
| Порядок выбирается только по направлению или чётности | При расширении `[P,A,B] → [P,A,B,C]` число подтверждений растёт и нужен SSN-first с барьером, а при расширении `[P,A,B,C] → [P,A,B,C,D]` оно не меняется и нужен другой порядок. Получаются четыре протокола с разным recovery. |
| Произвольный `target` в переходе, включая прямую замену нескольких реплик | Для `source=[P,A,B]`, `target=[P,A,C]` при доступных `A,B` и недоступном `C` source уже может безопасно выбрать кандидата, но двойная проверка перехода ждёт голос `C`. |
| Один состав в ZooKeeper, причём `D_ZK` — надмножество `D_SSN` | При `D_ZK=[P,A,B,C]` и SSN `ANY 1(A,B)` запись может быть только на `A`; после потери `P,A` голоса `B,C` соответствуют `D_ZK`, но не содержат запись. |
| Останавливать запись на время смены | При добавлении недоступной `C` к `[P,A,B]` primary перестаёт принимать записи до готовности `C`, хотя старая конфигурация `[P,A,B]` ещё безопасно подтверждает их через `A` или `B`. |

## Последствия

- Каждая смена состава выполняет один синхронный WAL-коммит после применения
  SSN `target`; основной цикл остаётся отзывчивым.
- Состояние перехода в ZooKeeper достаточно для продолжения после ошибки или
  рестарта, без локального состояния.
- Failover получает дополнительные проверки на время перехода и ждёт, если не
  может доказать сохранность данных.
- Чистое массовое сжатие сохраняет доступность surviving primary при потере
  всех реплик.
