# ADR-0005: Безопасная смена состава durability members

**Статус:** Принято
**Дата:** 2026-09-16

---

# Context

## Определения

- **Primary `P`** — текущий primary PostgreSQL.
- **Durability members `D`** — сохранённый в ZooKeeper состав узлов, которые могут
  подтверждать коммиты и участвовать в failover; `P ∈ D`.
- **Набор реплик `R(D, P)`** — `D − {P}`.
- **Необходимое для кворумного коммита число реплик** — `W(D) = ceil(|R(D, P)| / 2) = floor(|D| / 2)`.
- **SSN** — `synchronous_standby_names`, конфигурация PostgreSQL, задающая реплики, от которых primary ждёт подтверждение коммита.
  Возможные значения — `''` или `ANY W(D)(R(D, P))`.
- **Write quorum** — любой набор из `W(D)` реплик, который мог подтвердить кворумный коммит primary.
- **Read quorum** — любой набор из `Q(D)` проголосовавших во время фейловера реплик, где `Q(D) = |R(D, P)| − W(D) + 1`.
- **Зафиксированный состав** — единственный состав durability members, когда активного перехода нет.
- **Переход** — операция по изменению durability members. Содержит два равноправных состава
  (`source` и `target`). `target` указывает текущее направление завершения.
- **Cluster state** — единая CAS-запись ZooKeeper, содержащая `desired_primary`,
  текущую логическую операцию и состояние durability members.
- **Состояние кластерной операции** — тип (`idle`, смена durability members,
  failover либо switchover), фаза и её метаданные.
- **`state_id`** — UUID конкретной ревизии cluster state. Каждый успешный CAS
  записывает новый UUIDv4. Идентификаторы сравниваются только на точное
  равенство; числового или временного порядка между ними нет.
- **Состояние durability members** — зафиксированный состав и опционально переход,
  сохранённый внутри cluster state.
- **WAL-барьер** — синхронно закоммиченная в PostgreSQL запись с `state_id`
  снимка cluster state, разрешившего барьер, после применения
  SSN `target`. Доказывает, что write quorum `target` получил весь WAL primary
  до барьера.
- **CAS** — запись в ZooKeeper, которая может выполниться только в случае, если предыдущая версия ноды совпадает с той, которая была передана в запросе на запись.
- **Расширение** — переход, в котором `source ⊂ target`.
- **Сжатие** — переход, в котором `target ⊂ source`.
- **Замена** — переход, в котором ни один состав не является подмножеством другого.
- **Primary lock**, или **leader lock**, — эксклюзивная ephemeral-блокировка ZooKeeper, определяющая текущий primary.
- **Failover-manager lock** — эксклюзивная ephemeral-блокировка ZooKeeper,
  определяющая координатора активного failover.
- **`desired_primary`** — поле cluster state с хостом, которому разрешено быть
  или стать primary. Во время фейловера значение может быть `None`.
- **Quorum-member lease**, или **quorum lock**, — принадлежащая реплике ephemeral-блокировка
  `quorum/members/<fqdn>`. Она означает,
  что узел локально считает себя HA-репликой этого primary; lease не утверждает,
  что primary в данный момент видит её в `pg_stat_replication`.

ZooKeeper и PostgreSQL независимо хранят durability members и SSN. Эти два хранилища
нельзя изменить атомарно.

Полный состав `D`, переход и `desired_primary` хранятся в `/cluster_state`,
quorum-member lease — в `quorum/members/<fqdn>`, а grace period для вывода
задаётся `quorum_removal_delay`. Смена состава записывается как переход
`source`/`target`, а не как прямая перезапись списка.

Любой набор реплик, подтвердивших запись, размером `W(D)`, пересекается с
любым набором голосов размером `Q(D)`. Поэтому победитель, подтверждённый
`Q(D)` валидными голосами, не может не содержать WAL подтверждённой клиенту
записи.

Простой порядок «сначала ZooKeeper, затем SSN» небезопасен. Например, при
переходе `[P,A,B]` с `ANY 1(A,B)` к `[P,A,B,C]` с `ANY 2(A,B,C)` ZooKeeper
может уже разрешить новую конфигурацию, пока SSN ещё старый. Если запись есть
только на `A`, а `P` и `A` недоступны, голоса `B,C` могут выбрать узел без этой
записи.

Обратный порядок также небезопасен. Например, `[P,A,B,C]` с `ANY 2(A,B,C)` сжимается до
`[P,A,B]` с `ANY 1(A,B)`. Если SSN уже новый, а состав в ZooKeeper ещё старый, запись может быть
только на `A`. После потери `P` и `A` старый read quorum `{B,C}` выберет узел без этой записи.
Значит, нельзя выбирать порядок только по тому, расширяется или сжимается набор.

# Decision

## Роли хостов

- Реплика берёт или освобождает quorum-member lease в зависимости от своей
  готовности входить в durability members.
- Primary по lease holders формирует желаемый состав и безопасно применяет
  его к SSN и ZooKeeper:
  - ставит в ZooKeeper target durability members;
  - выставляет SSN и уходит на следующую итерацию;
  - коммитит транзакцию с новым SSN;
  - меняет source durability members и очищает target.

## Структура ZooKeeper

Пути указаны относительно cluster prefix.

| Путь | Назначение |
|---|---|
| `/cluster_state` | Единая CAS-запись: `state_id`, `desired_primary`, состояние кластерной операции и durability state. |
| `/quorum/members/<fqdn>` | Ephemeral quorum-member lease реплики. |
| `/leader` | Ephemeral lock текущего primary. |
| `/failover_manager` | Ephemeral lock координатора failover. |

`/cluster_state` хранит логические множества FQDN: каждый хост указан один раз,
порядок элементов не имеет значения. Зафиксированный состав хранится так:

```json
{
  "state_id": "d79a7d16-42f5-4b29-865b-1872c15da16d",
  "desired_primary": "P",
  "operation": {
    "type": "idle",
    "phase": null
  },
  "durability": {
    "members": ["P", "A", "B"],
    "transition": null
  }
}
```

Во время обычной смены состава `members` остаётся равным `source`, а в той же
записи появляется переход и меняется состояние кластерной операции:

```json
{
  "state_id": "572f63d9-a886-4e36-8fd3-d9c96a6d8139",
  "desired_primary": "P",
  "operation": {
    "type": "durability_transition",
    "phase": "apply_ssn"
  },
  "durability": {
    "members": ["P", "A", "B"],
    "transition": {
      "source": ["P", "A", "B"],
      "target": ["P", "A", "B", "C"]
    }
  }
}
```

- `members` — последний зафиксированный состав; он включает primary.
- `source` и `target` — равноправные значимые составы для failover;
  `target` также задаёт направление завершения перехода.
- `state_id` — UUID конкретной ревизии всей записи. Любое изменение, включая
  продвижение текущей фазы, изменение durability transition или начало
  failover, получает новый UUID.
- Версия znode используется для CAS и не дублируется в JSON.

Тип кластерной операции и durability transition — разные части состояния.
Обычная смена состава использует тип `durability_transition`. Failover или
switchover сохраняет собственный тип операции, но может создать, развернуть или
завершить durability transition в том же JSON. Каждое такое изменение, как и
смена фазы внешней операции, получает новый `state_id`. Поэтому для изменения
DM внутри switchover не нужно временно заменять тип операции или иметь второй
счётчик.

Завершение обычного перехода одним CAS заменяет `members` на `target`, очищает
`transition`, переводит операцию в `idle` и записывает новый `state_id`. Внутри
failover или switchover тот же CAS очищает transition и опционально продвигает фазу внешней
операции, не меняя её тип; `state_id` также заменяется.
Если `members` ещё не записан, автоматический failover не может доказать сохранность данных.

## Формирование желаемого состава

Реплика получает и удерживает quorum-member lease, когда одновременно выполнены
три локально проверяемых условия:

1. локальный PostgreSQL доступен и имеет роль `replica`;
2. хост входит в независимо заданный HA-состав;
3. локально сохранённый источник репликации (из primary_conninfo) совпадает с непустым `desired_primary`.

Узел освобождает lease, если он больше не replica, больше не входит в HA-состав
или непустой `desired_primary` не совпадает с его локальным источником репликации.
Если `desired_primary = None`, уже взятый lease сохраняется: исчезновение primary и окно
выборов не должны трактоваться как отказ всех реплик. Новый lease при
`desired_primary = None` не выдаётся.
Потеря ZooKeeper-сессии удаляет ephemeral lease.

Состояние streaming не входит в условия удержания lease. В частности, отсутствие
реплики в `pg_stat_replication` primary не заставляет её освобождать lease и не является
критерием вывода из `D`.

Обычный reconciliation primary формирует желаемый состав асимметрично:

- реплика, уже входящая в `D`, остаётся в нём, пока её lease существует;
- после исчезновения lease реплика удаляется только если он не вернулся за
  `quorum_removal_delay`; возврат lease сбрасывает grace period;
- реплика, ещё не входящая в `D`, добавляется, только если она удерживает lease,
  а primary видит её в `pg_stat_replication` в состоянии `streaming`.

После успешного promotion прежний primary может быть помечен для немедленного удаления,
поскольку после переключения прежний primary ещё не доказал готовность
работать как реплика нового primary. После return-to-cluster он может быть добавлен заново по
обычным условиям ввода. Немедленная пометка обходит только
grace period, но не протокол безопасной смены `D`, описанный ниже.

Grace period влияет только на выбор момента начала изменения состава. Добавление и удаление всё равно выполняются
через переход `source`/`target` и WAL-барьер.

Каждая смена состава выполняется одним протоколом. Во время перехода `source` и `target` равноправны:
failover рассматривает оба состава как потенциально действующие на момент отказа.
`target` определяет только направление выполнения следующих шагов.

1. Primary CAS-записью создаёт intent: записывает новый `state_id`, переводит
   операцию в `durability_transition` и сохраняет `source`/`target`.
2. Primary применяет SSN, вычисленный для `target`, по правилам ниже.
3. primary записывает WAL-барьер с `state_id` снимка, разрешившего этот
   шаг, и коммитит его с
   `synchronous_commit = on`:

   ```sql
   BEGIN;
   SET LOCAL synchronous_commit = on;
   CREATE TABLE IF NOT EXISTS public.pgconsul_durability_barrier (
       singleton boolean PRIMARY KEY CHECK (singleton),
       state_id uuid NOT NULL
   );
   TRUNCATE TABLE public.pgconsul_durability_barrier;
   INSERT INTO public.pgconsul_durability_barrier
       (singleton, state_id) VALUES (true, '<state_id>');
   COMMIT;
   ```

4. Только после успешного барьера primary CAS-записью заменяет переход одним
   зафиксированным составом `target`. Для обычной смены операция становится
   `idle`; внутри внешней операции сохраняется её тип и продвигается её фаза.

### Распространение SSN внутри PostgreSQL

SSN не меняется атомарно во всех процессах PostgreSQL:

1. pgconsul записывает `synchronous_standby_names` и вызывает reload.
2. Postmaster перечитывает конфигурацию и посылает SIGHUP дочерним процессам.
   Новый backend или WAL sender, созданный после этого, наследует новое значение.
3. Каждый уже работающий WAL sender обрабатывает SIGHUP самостоятельно. Он хранит
   разобранный SSN в локальной памяти и через `SyncRepInitConfig()` публикует свой
   `sync_standby_priority` в общей памяти. Разные sender'ы могут применить reload
   в разное время.
4. Обычный backend не использует полный список SSN при коммите. Checkpointer после
   своего SIGHUP записывает в общей памяти только `SYNC_STANDBY_DEFINED` — признак
   того, пуст SSN или нет. При установленном флаге backend ставит commit LSN в
   очередь ожидания. Конкретный quorum вычисляет WAL sender, получивший ответ от
   реплики: режим `FIRST`/`ANY` и `num_sync` он берёт из своего локального
   `SyncRepConfig`, а кандидатов, их `sync_standby_priority` и позиции
   `write`/`flush`/`apply` — из shared memory всех sender'ов.

`SHOW synchronous_standby_names` в новом (= только что форкнут, а не взят из пула)
SQL-соединении показывает значение в этом backend и косвенно подтверждает, что postmaster начал применять новую
конфигурацию. Оно не подтверждает обработку SIGHUP checkpointer'ом или уже
работающими WAL sender'ами.

После записи SSN и запроса reload pgconsul **обязательно завершает текущую
итерацию**, не рестартит sender'ы и не запускает WAL-барьер. На следующей итерации
он заново читает cluster state и проверяет SSN через новое прямое соединение.
Эта граница итераций — явный временный костыль, а не синхронизация с PostgreSQL:
она только снижает вероятность того, что при переходе `async → sync` checkpointer
ещё не выставил `SYNC_STANDBY_DEFINED`, а так же вероятность того, что sender'ы не применили SSN.

### Нерешённые проблемы применения SSN

Гонка с checkpointer **не закрыта**. PostgreSQL 14 не предоставляет SQL-подтверждения
обработки им SIGHUP, а `SHOW` в другом backend этого не доказывает. Поэтому после
перехода от пустого SSN к непустому commit может пройти как async, даже если файл
конфигурации, postmaster и sender'ы уже используют `target`. Переход на следующую
итерацию лишь уменьшает окно этой гонки. При переходе от непустого SSN к пустому
обратная задержка приводит к лишнему ожиданию commit'ов, то есть к проблеме
доступности, а не сохранности данных.

Применение полного SSN уже работающими sender'ами надёжно не подтверждается.
Дефолтная реализация pgconsul не завершает sender'ы после reload: на следующей итерации
она проверяет `SHOW` в новом прямом соединении и переходит к WAL-барьеру. Это не
доказывает, что каждый sender обработал SIGHUP и использует `target`.

Разные sender'ы могут одновременно использовать разные версии SSN.
`SyncRepReleaseWaiters()` использует `num_sync` из локальной конфигурации
вызвавшего его sender'а, но список кандидатов строит по `sync_standby_priority`,
опубликованным всеми sender'ами. Поэтому во время reload commit может подтвердить
смешанный набор, не являющийся write quorum ни `source`, ни `target`. Например,
при переходе `ANY 1(A,B) → ANY 2(A,B,C)` старый sender может всё ещё требовать
одно подтверждение, но уже увидеть `C` кандидатом после того, как sender `C`
применил новый SSN. Двойная проверка `source` и `target` при failover такой набор
не покрывает. Это остаётся нерешённой проблемой сохранности данных.

Одного изменения файла конфигурации, границы итераций или успешного `SHOW` для
полного подтверждения применения SSN недостаточно. При переходе с пустого SSN
на непустой отдельно остаётся нерешённой гонка с `SYNC_STANDBY_DEFINED`, описанная
выше.

#### Потенциальный костыль: последовательный рестарт sender'ов

Как временное решение можно после наблюдения `target` в новом backend
последовательно перезапустить sender'ы, обслуживающие `source ∪ target`:

1. Запомнить PID действующих sender'ов для текущего `state_id`.
2. В одной итерации завершить не более одного старого sender'а и сразу закончить
   итерацию.
3. В следующих итерациях дождаться исчезновения старого PID. Для реплики из
   `target` дополнительно дождаться нового sender'а с другим PID в состоянии
   `streaming`; только затем переходить к следующему sender'у.
4. После замены всех sender'ов выполнить WAL-барьер. После рестарта pgconsul или
   потери локального прогресса начать проверку и замену заново.

Этот алгоритм не входит в дефолтную реализацию pgconsul. Он опирается на то, что новый
процесс наследовал конфигурацию postmaster, но не наблюдает его локальный
`SyncRepConfig`. Он обеспечивает eventual convergence, но не исключает смешанный
quorum во время неодновременной обработки уже разосланного SIGHUP и не закрывает
гонку с checkpointer.

Кроме того, завершение sender'а разрывает соединение walreceiver. Startup process
реплики снова перебирает archive и локальный `pg_wal`, затем подключается к
primary; новый sender остаётся в `catchup`, пока не обнулит send lag. Если
`write_lsn` реплики сильно отстаёт, ожидание нового sender'а в `streaming`
включает чтение доступного архива и последующий catchup. Оно может быть очень
долгим или не завершиться при постоянной высокой нагрузке, блокируя весь переход
durability members. Пока sender не вернулся в `streaming`, реплика не участвует
в synchronous quorum; при отсутствии запасных реплик блокируются и commit'ы.

Если появится инструмент, подтверждающий установленный `SYNC_STANDBY_DEFINED`,
локальный SSN и опубликованный priority каждого sender'а, а также новое значение
postmaster для будущих sender'ов, то commit records, созданные после такого
подтверждения, будут ожидать `target`. Локальный SSN уже работающих обычных
backend'ов при этом не важен: они используют общий признак непустого SSN.
Гарантия относится только к транзакциям с `synchronous_commit`, требующим
синхронного подтверждения; клиент по-прежнему может явно выбрать `off` или `local`.

`WalSndCtl->lsn` не версионирован конфигурацией и может содержать позицию,
освобождённую до полной сходимости. Поэтому границей гарантии должен оставаться
WAL-барьер, выполненный после подтверждения конфигурации
Барьер переносит на `target` весь предшествующий WAL,
включая транзакции, начавшие commit до сходимости. Без подтверждения SSN барьер
мог бы подтвердиться по `source` или смешанному набору; без барьера старые commit'ы
могли бы остаться только на прежнем наборе. До завершения обоих шагов переход в
ZooKeeper сохраняет оба значимых состава, но этого недостаточно для смешанного
набора sender'ов, описанного выше.

Успешный синхронный commit барьера, выполненный после достоверного подтверждения
общего флага и конфигурации всех sender'ов, означает, что весь WAL primary до
барьера был сброшен набором подтверждающих реплик из `target`. Этот набор
пересекается с любым read quorum `target`; последующие транзакции уже защищены
SSN `target`. Текущая временная процедура не даёт такого строгого подтверждения
из-за явно перечисленных выше гонок.

Барьер выполняется неблокирующе: незавершённая за таймаут команда не блокирует основную
итерацию pgconsul. Таймаут или потеря соединения не считаются успехом, поскольку
локальный коммит мог завершиться до получения подтверждения клиентом.

## Операции с PostgreSQL и ожидаемый результат

Таблица сводит операции, от которых зависит смена состава. Пометка кандидата
сама по себе не меняет `D`: вывод или ввод происходит по описанному выше протоколу.

| Операция | Что должно быть верно после неё | Почему |
|---|---|---|
| Отметить реплику кандидатом на вывод из `D` из-за несовпадения локального источника с непустым `desired_primary` | После безопасного завершения смены состава реплика, не способная подтверждать коммиты нужного primary, выведена из `D`. | Она настроена получать WAL другого primary и не может подтверждать WAL текущего. При `desired_primary = None` уже взятый lease сохраняется и эта причина вывода не возникает. |
| Отметить хост кандидатом на вывод из `D`, потому что его PostgreSQL больше не replica | После безопасного завершения смены состава хост, не способный подтверждать коммиты как реплика, выведен из `D`. | Остановленный узел или узел в роли primary не принимает WAL текущего primary как HA-реплика. |
| Отметить реплику кандидатом на вход в `D` только после появления её sender'а в `pg_stat_replication` со статусом `streaming` | После безопасного завершения смены состава реплика, способная подтверждать коммиты, добавлена в `D`. | Потоковое соединение показывает, что primary может отправлять ей WAL; готовность подтвердить весь прежний WAL дополнительно доказывает барьер. |
| Применить SSN для новых транзакций: выставить `target`, завершить итерацию и на следующей итерации проверить `SHOW` в новом прямом соединении | Postmaster начал применять SSN `target`; новые процессы наследуют это значение. | Граница итераций — временный костыль. Она не подтверждает `SYNC_STANDBY_DEFINED` при `async → sync` и применение конфигурации уже работающими sender'ами. Дефолтная реализация не рестартит sender'ы. |
| Выполнить LSN-барьер: записать маркер с `state_id` и получить успешный ответ на `COMMIT` при `synchronous_commit = on` | При фактически применённом непустом SSN `target` его write quorum содержит весь WAL primary до барьера, в том числе данные, подтверждённые write quorum `source`; после этого по `target` возможен failover без их потери. | Подтверждённый SSN защищает новые commit'ы, а барьер переносит прежний WAL на `target`. Текущая временная процедура не даёт строгого доказательства применения из-за гонок checkpointer и смешанных конфигураций sender'ов. При пустом `target` commit только локальный; таймаут или разрыв соединения не считаются успехом. |

## Восстановление перехода после рестарта pgconsul на текущем мастере

| Точка остановки | Сохранённое состояние | Действие после рестарта |
|---|---|---|
| До intent | Прежний зафиксированный состав | Начать переход заново. |
| После intent, до SSN | `source`, `target`, текущий `state_id` | Применить SSN `target`, завершить итерацию и на следующей итерации проверить значение через новое прямое соединение. |
| После SSN, до барьера | Переход сохранён | Повторить применение и проверку SSN, затем выполнить барьер. |
| После барьера, до финального CAS | Переход сохранён | Повторить применение и проверку SSN, барьер и CAS для `target`. |
| После финального CAS | Зафиксирован один состав `target`, перехода нет | Считать операцию завершённой. |

Повторное применение SSN, барьер и CAS идемпотентны, пока primary не сменился.
Конфликт CAS требует заново прочитать состояние; он не является признаком
успешного завершения.

## Допустимые формы перехода

Обычная сверка выполняет расширение по одному хосту. Сжатие может
удалить несколько хостов за один переход. Замена реплик представляется как
несколько однохостовых расширений, затем одно сжатие.

Произвольная прямая замена может сделать failover излишне недоступным, пока
переход не завершён: для `source=[P,A,B]`, `target=[P,A,C]` потребуются голоса
и от `B`, и от `C`, хотя один `source` мог бы выбрать кандидата. Сжатие
этой проблемы не создаёт, так как не вводит новую реплику.

В частности, surviving primary может сразу сжать `[P,A,B,C]` до `[P]`, если
все реплики потеряны. SSN становится асинхронным, барьер коммитится локально,
и доступность записи восстанавливается. До добавления новой реплики такой
кластер намеренно не даёт автоматическому failover гарантий сохранности.

## Владение и блокировки

Сменой состава управляет один участок основной итерации. Если перехода нет, он сравнивает
желаемый состав с зафиксированным и при расхождении создаёт переход. Если переход есть, он выполняет
его следующий шаг. Этот участок вызывается после обновления maintenance state. Менять состав и SSN может
только узел, владеющий leader lock.

Leader lock является единственным источником полномочий для обычной смены
состава; отдельный persistent owner в cluster state не хранится. Перед каждым
шагом узел читает cluster state и действует только при точном совпадении
`state_id`, типа и фазы операции. Внешний результат шага помечается этим
`state_id`. Запись следующего состояния выполняется CAS по прочитанной версии,
проверяет такой результат и записывает новый UUID.

Обычный reconciliation может начать новый переход только из `idle`. Пока активен
`durability_transition`, тот же primary продолжает его, читая актуальный
`state_id` перед каждым шагом и заменяя его каждым CAS. CAS начала failover
атомарно меняет тип операции и записывает новый `state_id`, сохраняя
`members`, `source` и `target`. После этого уже
подготовленная запись primary использует старую версию и завершается конфликтом
CAS, а новые шаги смены состава запрещены. Поэтому failover замораживает точное
состояние перехода без второго сериализующего лока.

Кластерная операция другого типа может содержать durability transition как
подсостояние. Его создаёт и продвигает координатор этой операции, а обычный
reconciliation параллельно этого не делает. Тип операции при этом не меняется,
но каждый CAS durability-подсостояния заменяет общий `state_id`. Такие
операции не заменяют зафиксированный состав прямой записью.
Правила изменения или завершения перехода во время failover описаны в
[ADR-0006](ADR-0006-safe-failover.md). Детальный протокол switchover находится
вне этого ADR; он обязан использовать тот же cluster state и не допускать
параллельную смену состава независимым писателем.

# Альтернативы

| Вариант | Проблемная ситуация |
|---|---|
| Всегда «ZooKeeper, затем SSN» | `[P,A,B]`, `ANY 1(A,B)` меняется на `[P,A,B,C]`, `ANY 2(A,B,C)`. Пока SSN старый, запись может быть только на `A`; после потери `P,A` голоса `B,C` выберут узел без неё. |
| Всегда «SSN, затем ZooKeeper» | `[P,A,B,C]`, `ANY 2(A,B,C)` сжимается до `[P,A,B]`, `ANY 1(A,B)`. Пока ZooKeeper старый, запись может быть только на `A`; после потери `P,A` старый quorum `B,C` выберет узел без неё. |
| Порядок выбирается только по направлению или чётности | При расширении `[P,A,B] → [P,A,B,C]` число подтверждений растёт и нужен SSN-first с барьером, а при расширении `[P,A,B,C] → [P,A,B,C,D]` оно не меняется и нужен другой порядок. Получаются четыре протокола с разным recovery. |
| Произвольный `target` в переходе, включая прямую замену нескольких реплик | Для `source=[P,A,B]`, `target=[P,A,C]` при доступных `A,B` и недоступном `C` source уже может безопасно выбрать кандидата, но двойная проверка перехода ждёт голос `C`. |
| Один состав в ZooKeeper, причём `D_ZK` — надмножество `D_SSN` | При `D_ZK=[P,A,B,C]` и SSN `ANY 1(A,B)` запись может быть только на `A`; после потери `P,A` голоса `B,C` соответствуют `D_ZK`, но не содержат запись. |
| Останавливать запись на время смены | При добавлении недоступной `C` к `[P,A,B]` primary перестаёт принимать записи до готовности `C`, хотя старая конфигурация `[P,A,B]` ещё безопасно подтверждает их через `A` или `B`. |
| Удалять по отсутствию в `pg_stat_replication` | Нарушение сети или PostgreSQL на primary может одновременно скрыть несколько исправных реплик и вызвать ложное массовое сжатие `D`. |
| Использовать `alive` lock вместо quorum-member lease | `alive` показывает только доступность локального PostgreSQL и ZK-сессии; он не привязан к HA-составу и `desired_primary`. |
| Освобождать lease при `desired_primary = None` | Все lease исчезнут именно во время failover, что ложно выглядит как одновременный отказ всех реплик. Electorate фиксируется из `D` отдельно, но для локальной membership-семантики такое исчезновение неверно. |
| Одинаково требовать streaming для ввода и удержания | Проверка streaming нужна, чтобы не добавлять заведомо неготовый узел, но её использование для вывода возвращает зависимость от одностороннего наблюдения primary. |
| Хранить `desired_primary`, durability transition и состояние failover в независимых CAS-нодах | Разные держатели локов могут успешно изменить разные ноды и оставить сочетание состояний, которое никогда не было одной логической конфигурацией. Для восстановления понадобятся отдельные правила каждой частичной записи. |
| Хранить persistent owner логической операции рядом с ephemeral manager lock | После смерти процесса owner остаётся, а новый держатель lock должен отдельно перехватывать его. Lock и owner становятся двумя источниками права записи и могут рассинхронизироваться. |

# Последствия

- Каждая смена состава дожидается применения SSN `target` и выполняет один
  синхронный WAL-коммит; основной цикл остаётся отзывчивым.
- Состояние перехода в ZooKeeper достаточно для продолжения после ошибки или
  рестарта без персистентного локального состояния.
- Failover проверяет оба состава незавершённого перехода по правилам
  [ADR-0006](ADR-0006-safe-failover.md).
- Один cluster state сериализует смену состава, failover и изменение
  `desired_primary`; конфликт CAS всегда требует перечитать всю логическую
  конфигурацию.
- Массовое сжатие сохраняет доступность surviving primary при потере
  всех реплик.
- Обычный вывод реплики из `D` зависит только от её quorum-member lease и grace period,
  а не от наблюдаемой primary репликации.
- Живая HA-реплика с правильным локальным источником может оставаться в `D`, даже если
  она не реплицируется. Это намеренная плата доступностью за то, что primary-side network
  failure не сжимает durability-состав и не ослабляет гарантии.
- До появления наблюдаемого подтверждения от checkpointer переход на следующую
  итерацию только уменьшает окно async commit при `async → sync`.
- Дефолтная реализация не подтверждает применение полного SSN каждым sender'ом;
  смешанный quorum во время неодновременного применения SIGHUP остаётся
  нерешённой проблемой. Последовательный рестарт sender'ов описан только как
  потенциальный костыль и может надолго заблокировать переход на отстающей
  реплике.
